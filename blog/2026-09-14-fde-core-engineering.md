# FDE 技能栈之一：核心工程能力——驻场工程师的立身之本

> 本文是「FDE 技能栈全景图」系列的第一篇支柱展开文章，对应主文中的「支柱一：核心工程能力」。
> 系列总览见：[FDE 技能栈全景图](./2026-09-14-fde-skill-stack-pillar.md)

## 为什么核心工程能力是第一支柱

先说一个驻场工程师都会遇到的场景：

你到客户现场的第三天，业务负责人说：「我们 ERP 里的库存数据和 WMS 系统对不上，你能不能先看看？」没有需求文档，没有接口说明，对方只能给你两个数据库的只读账号。客户 IT 告诉你：生产环境不能直连，导数据要走审批，预计三个工作日。 meanwhile，你的项目经理在群里问：什么时候能出第一版分析？

这个场景里没有一件事是「写代码」，但每一件事最终都要靠工程能力落地：你得用 SQL 摸清两个库的表结构，写脚本做对账，搭一个最小管道把数据定期拉出来，再把它部署到客户那台没有外网的 Linux 服务器上。

FDE 和办公室里的工程师最大的区别在于：**现场没有分工**。没有专门的前端、没有 DBA、没有运维，客户也不会接受「这不是我职责范围」。核心工程能力——全栈开发、数据工程、基础设施与部署——决定了你能不能在没有支援的环境里独立把事做成。软技能决定你的天花板，但硬技能决定你能不能活到展示软技能的那一天。

本文把这一支柱拆成三块逐一展开：全栈开发、数据工程（重中之重）、基础设施与部署。每一块都按「是什么、怎么做、常见坑」来写，最后给出学习路径和自测清单。

## 一、全栈开发能力：能独立交付一个完整系统

### 1.1 定位：够用的广度，一门精通

FDE 对全栈的要求和普通互联网公司的「全栈」不一样。你不需要精通前端性能优化或高并发架构，你需要的是：**从数据库到浏览器，一个人能把一条链路走通**。

现实中 FDE 交付的系统大多是：内部工具、数据看板、对账平台、流程审批小应用。用户量在几十到几百，性能几乎不是瓶颈，可用性和交付速度才是。

建议的技术组合（按使用频率排序）：

- **后端主力语言：Python**。数据工程、脚本、Web 开发通吃，FDE 场景下性价比最高。配合 **FastAPI** 可以快速搭出带自动文档的 REST API。Java/Scala 主要在大数据客户（Spark 重度场景）使用；TypeScript/Node.js 作为第二选择。
- **前端：React + Ant Design**。内部工具场景下 Ant Design 的表格、表单、筛选组件几乎覆盖了 80% 的需求。不需要审美，需要信息架构清楚。
- **数据可视化：ECharts 或 Plotly**。客户最终要的往往是「一张能看懂的图」。ECharts 中文文档好、企业客户接受度高。

### 1.2 必须熟练的几件事

**认证与权限。** 客户环境几乎必问权限。至少要能讲清楚并实现：

- JWT 的签发与校验流程；
- RBAC（基于角色的访问控制）的最小实现：用户、角色、权限三张表；
- 对接客户已有的认证体系（LDAP/AD 域、OAuth2/OIDC）——传统企业客户大量使用 AD 域，提前了解 `python-ldap` 或各框架的 LDAP 集成方式，能省掉现场现学的时间。

**异步任务。** 数据同步、报表生成这类耗时操作不能同步阻塞接口。Python 生态下 Celery + Redis 是常见组合；需求简单时，一个 `cron` + 脚本的组合往往比引入消息队列更务实——客户环境多一个组件就多一分审批和维护成本。

**交付形态要多样。** FDE 的产出不一定是 Web 应用：

- CLI 工具（给客户 IT 用的运维脚本）；
- Jupyter Notebook（数据分析报告，可直接导出 HTML/PDF 给业务方）；
- Streamlit 小应用（48 小时原型的主力，见支柱二）；
- 定时任务脚本（数据对账、日终跑批）。

### 1.3 常见坑

- **过度工程化**。给一个 50 人用的内部工具上微服务、上 K8s，是最典型的新手错误。单机 Docker Compose 能跑的，就别引入编排系统。现场系统的第一诉求是「客户 IT 能接手维护」。
- **用客户环境里没有的技术栈**。你的 Clojure 写得再好，客户没人能维护，验收就是灾难。技术选型的第一原则是**匹配客户团队的维护能力**，第二才是你的偏好。
- **忽略 IE/老旧浏览器**。部分政企客户的终端环境停留在旧版本浏览器，交付前务必在客户的真实终端上验证。这个问题在 Demo 当天暴露是最尴尬的。

## 二、数据工程能力：FDE 的重中之重

如果只能把一项技能练到极致，选数据工程。绝大多数 FDE 项目的本质都是：**把客户散落各处的脏数据接进来、洗干净、整合成能用的东西**。

### 2.1 SQL：练到肌肉记忆级

「熟练 SQL」在 FDE 语境下的标准是：拿到一个陌生数据库的连接，**两个小时内**你能搞清楚核心表结构、数据量级、数据质量的主要问题，并写出一个能回答业务问题的查询。

必须达到不假思索程度的能力：

- 复杂多表 JOIN（含自连接、非等值连接）；
- 窗口函数：`ROW_NUMBER()`、`LAG()/LEAD()`、`SUM() OVER (PARTITION BY ...)`——去重、取最新一条、环比同比全靠它们；
- CTE（`WITH` 子句）组织复杂查询，现场没人有耐心看你 300 行的嵌套子查询；
- 递归 CTE 处理层级数据（组织架构、BOM 物料清单在制造业客户中极常见）；
- 条件聚合：`SUM(CASE WHEN ... THEN 1 ELSE 0 END)`，一行 SQL 出透视表。

一个真实的日常场景——用窗口函数做数据去重。客户表里同一个业务单号有多条记录（系统重复同步导致），你要取每个单号最新的一条：

```sql
WITH ranked AS (
    SELECT
        order_no,
        status,
        amount,
        updated_at,
        ROW_NUMBER() OVER (
            PARTITION BY order_no
            ORDER BY updated_at DESC
        ) AS rn
    FROM raw_orders
)
SELECT order_no, status, amount, updated_at
FROM ranked
WHERE rn = 1;
```

这个模式（`ROW_NUMBER` 取每组第一条）在现场的使用频率高到值得背下来。

**方言切换**也是刚需。传统企业客户大量使用 Oracle，金融行业常见 DB2，国企有达梦、人大金仓等国产库，大数据场景是 Hive/Spark SQL。常见差异：分页（`LIMIT` vs `ROWNUM` vs `OFFSET FETCH`）、字符串拼接（`||` vs `CONCAT`）、日期函数。建议整理一份自己的方言速查表，随项目积累。

**数据探查三板斧**——拿到任何一张陌生表，先跑这三个查询：

```sql
-- 1. 行数与时间范围
SELECT COUNT(*), MIN(created_at), MAX(created_at) FROM t;

-- 2. 关键字段的分布与空值率
SELECT status, COUNT(*), COUNT(*) * 1.0 / (SELECT COUNT(*) FROM t) AS pct
FROM t GROUP BY status ORDER BY pct DESC;

-- 3. 主键唯一性验证（数据质量的核心检查）
SELECT order_no, COUNT(*) AS cnt
FROM t GROUP BY order_no HAVING COUNT(*) > 1;
```

这三板斧能让你在十分钟内对一张表的「脏法」有基本判断。

### 2.2 数据管道：设计原则比工具重要

调度工具（Airflow / Dagster / Prefect）学会一个就够，概念是相通的。真正决定管道质量的是下面几个原则，无论用什么工具都适用：

**幂等写入。** 同一个任务跑两次，结果必须和跑一次一样。现场管道一定会因为各种原因重跑（网络抖动、上游数据迟到、客户误操作），非幂等的管道重跑一次就是一次数据事故。常见实现：按业务主键 `INSERT ... ON CONFLICT DO UPDATE`（PostgreSQL）或 `MERGE INTO`（Oracle/Spark），或者「先删分区再写入」。

**增量同步。** 全量拉取在数据量上去之后必然不可行。标准做法是基于更新时间戳的水位线（watermark）：

```sql
SELECT * FROM source_table
WHERE updated_at > :last_watermark
  AND updated_at <= :current_watermark;
```

注意坑：只依赖 `updated_at` 会漏掉「同步窗口内被修改但时间戳没更新」的记录，重要数据要定期做全量对账（reconciliation）兜底。

**失败要可见、可重试。** 管道挂了的第二天被客户发现数据没更新，是信任杀手。最低要求：失败有告警（邮件/钉钉/企业微信 webhook 都行）、重跑不会把数据搞乱（幂等）、有地方能查「每天跑了多少条、成功没有」——一张最简单的运行日志表都比没有强。

**先接数，后清洗，分层存放。** 不要边抽边洗成最终形态。按 ODS（原始层）→ DWD（明细层）→ DWS/ADS（汇总层）的思路分层，原始数据原样落地一份。业务规则一定会变，原始数据在你就能重算；原始数据没留，规则变了就是事故。

### 2.3 大数据生态：按客户环境选学

- **Spark** 是 Palantir 系 FDE 的标配，PySpark 的 DataFrame API 与 SQL 二选一即可上手。核心要理解：分区、shuffle、广播 join 这些概念，否则写出的任务慢十倍你都不知道为什么。
- **Hadoop/Hive** 在传统行业客户（银行、运营商、能源）仍然大量存在，遇到时不必恐慌——HiveQL 和你会的 SQL 差异不大，主要适应它的分区表思维。
- 不建议在没接触真实集群前深挖调优，先有「能在集群上跑通一个 ETL 任务」的端到端经验更重要。

### 2.4 数据建模：把混乱抽象成干净

客户的数据现状通常是：十几个系统、上百张表、字段命名随心所欲、`status` 字段有 17 种含义。你的工作是把它抽象成少数几个干净的实体和关系。

基本功包括：

- **维度建模**：事实表 + 维度表的星型模型，Kimball 的《数据仓库工具箱》是标准教材；
- **缓慢变化维（SCD）**：客户信息变了，历史记录怎么办。至少要会 Type 2（拉链表）的实现——这在金融和政务客户是硬性要求；
- **本体（Ontology）思维**：Palantir Foundry 的核心概念。本质是「以业务对象为中心建模，而不是以表为中心」——订单、设备、工单这些业务对象及其关系构成语义层，应用和分析都基于对象而非裸表。即使不用 Foundry，这种思维方式对组织混乱数据极有帮助。

一个实操建议：建模前，**先和客户一起把核心业务流程图画出来**，每个流程节点标注「这个动作在哪个系统里产生什么数据」。建模的错误大多不是技术错误，是业务理解错误。

### 2.5 数据工程的常见坑

- **低估数据脏的程度**。「客户说数据质量还可以」的实际含义通常是「没人认真查过」。默认假设：主键有重复、外键有孤儿、时间字段有时区混乱、金额字段有单位不一致（元/万元混用）。
- **管道没有数据质量校验**。每天跑完管道加几个断言：行数波动是否超过阈值、关键字段空值率、对账总额是否一致。Great Expectations 或 Pandera 可以做，自己写 SQL 断言也完全够。
- **在客户的生产库上直接跑重查询**。现场大忌。先谈清楚只读副本、测试环境或定时导出的方案。

## 三、基础设施与部署：决定交付速度的隐形能力

客户现场的现实是：隔离网（无外网）、老旧系统、任何软件安装要走审批。部署能力差，代码写得再好也交付不出去。

### 3.1 Linux 基本功：排查问题的能力是底线

现场没有运维帮你，以下必须是条件反射：

```bash
# 日志排查
tail -f app.log                    # 跟踪实时日志
grep -i "error" app.log | tail -50 # 找最近的错误
journalctl -u myapp --since "1 hour ago"  # systemd 服务日志

# 进程与端口
ps aux | grep python               # 进程是否活着
ss -tlnp | grep 8080               # 端口被谁占用（比 netstat 快）
kill -9 <pid>                      # 实在没办法时的终局手段

# 网络诊断（客户现场网络问题极常见）
curl -v http://internal-api:8080/health   # 验证连通性与响应
dig internal-db.corp.local                # DNS 解析是否正常
ping -c 3 10.0.1.5                        # 基础连通性

# 磁盘与内存（离线环境磁盘写满是高频事故）
df -h
du -sh /var/lib/docker/* | sort -h | tail
free -h
```

建议练熟 `vim` 的基本操作——客户的堡垒机里往往只有它。

### 3.2 Docker：隔离网交付的标配

容器化是 FDE 交付的主流形态：把应用和所有依赖打包成镜像，客户环境只要装 Docker 就能跑。

**离线环境交付的核心操作：**

```bash
# 在有网的机器上构建并导出
docker build -t myapp:1.2.0 .
docker save myapp:1.2.0 | gzip > myapp-1.2.0.tar.gz

# 通过客户允许的介质（U盘/摆渡机）拷入内网后导入
gunzip -c myapp-1.2.0.tar.gz | docker load
```

配套建议：

- **镜像尽量小**：用 `python:3.x-slim` 基础镜像而非完整版，多阶段构建。离线环境下 2GB 的镜像光拷贝就要走一次审批流程。
- **Docker Compose 管理多组件**：应用 + 数据库 + Redis 一个 `docker-compose.yml` 搞定，`docker compose up -d` 一条命令起全栈。这比给客户一份十页的部署手册有效得多。
- **数据卷挂载点写进文档**：容器删了数据还在，这是客户 IT 最关心的问题。
- Kubernetes 在大多数 FDE 单点交付场景是过剩的，除非客户已有 K8s 平台。会基本概念即可，不必深入。

### 3.3 CI/CD：在客户内网搭最小流水线

哪怕是内网、哪怕只有你一个人开发，也要有最小化的流水线。价值在于：每次改动能自动跑测试和构建，交付物是可复现的，而不是「某台笔记本上打包出来的」。

- **GitLab CI** 是私有化场景的主流（GitLab 有免费社区版，客户内网可自建）。一个最小可用的 `.gitlab-ci.yml` 通常只有三个阶段：`test`（跑单元测试）、`build`（打镜像）、`deploy`（推到客户的镜像仓库或导出 tar 包）。
- **GitHub Actions** 适用于客户允许用云服务的场景。
- 没有条件搭 CI 时，一个本地的 `make release`（或 `build.sh`）脚本把「测试 → 构建 → 导出」串起来，也能达到 80% 的效果。关键是**构建过程不依赖人的记忆**。

### 3.4 Git 协作规范：和客户团队混编时的刚需

驻场后期常出现客户工程师参与开发的情况。此时要带头建立：

- 分支模型：简单的 trunk-based 或 `main + feature 分支`，不要给客户的初级团队上 GitFlow；
- MR/PR + Code Review 流程；
- commit message 规范（格式统一即可，不必苛求 Conventional Commits）；
- `.gitignore` 里坚决排除密钥和配置文件——**把客户的生产密码提交进 Git 是重大事故**，发生过不止一次。密钥用环境变量或 `.env`（并加入 `.gitignore`）。

### 3.5 云与私有化

- 至少熟悉一家云（AWS / Azure / 阿里云）的核心服务：对象存储、RDS、虚拟机、IAM。出海项目基本是 AWS/Azure。
- 同时要有「纯私有化、无云」的预案：MinIO 替代 S3、自建 PostgreSQL 替代 RDS、Nginx 替代云负载均衡。这些开源替代品最好在去现场前就练过一遍，现场的每一小时都很贵。

## 四、学习路径建议

按「能在现场活下来」的优先级排序：

**第 1 个月：SQL + Python 基础**
- SQL：LeetCode Database 题刷完中等难度，重点练窗口函数；找一份公开数据集（如 Kaggle 的电商数据集）自己导入 PostgreSQL 做探查练习。
- Python：FastAPI 官方教程过一遍，能独立写出一个带认证和数据库的 CRUD API。
- 验收标准：随便给你一张陌生表，30 分钟内写出一个有业务意义的分析查询。

**第 2-3 个月：数据管道 + Linux/Docker**
- 用 Airflow 或 Dagster 搭一个完整的小管道：从 API 或数据库抽数 → 清洗 → 写入数仓分层 → 加数据质量断言 → 失败告警。
- Docker：把这个管道连同数据库整体容器化，练习 `docker save/load` 离线交付流程。
- Linux：在自己的机器上裸机部署一遍整个系统，不许用任何图形界面。

**第 4-6 个月：端到端模拟实战**
- 给自己出题：模拟一个「客户现场」——找一个公开的多源数据集（故意挑脏的），两周内做出一个带数据管道、权限、可视化看板的完整应用，并用 Docker Compose 一键交付。
- 如果目标公司技术栈涉及 Spark，这个月把 PySpark 在本地集群（Docker 起单机 Spark）跑通。

**进入现场后：按需补课**
- 客户的方言（Oracle/达梦）、客户的行业系统（ERP/MES/HIS）、Foundry 或客户的数据平台——这些在现场学的效率远高于自学，前提是你的基础功扎实。

以下问题如果能全部答「能」，核心工程能力基本过关：

**SQL 与数据**
- [ ] 能不看文档写出窗口函数实现「每组取最新一条」
- [ ] 能在 PostgreSQL 和 Oracle 之间切换写分页、字符串、日期函数
- [ ] 拿到陌生库能在一小时内摸清核心表和数据质量问题
- [ ] 能解释并实现幂等写入、增量同步水位线
- [ ] 能画出星型模型并解释 SCD Type 2 的实现

**全栈开发**
- [ ] 能独立交付一个带 JWT 认证 + RBAC 权限 + 前端列表页/图表的完整应用
- [ ] 能在 48 小时内用 Streamlit 或 FastAPI + React 做出可演示原型
- [ ] 写的系统客户团队能看懂、能接手维护

**基础设施**
- [ ] 能用 `grep/tail/ss/df` 在陌生 Linux 机器上独立排查「服务挂了」「端口不通」「磁盘满了」

- [ ] 知道如何把密钥排除在 Git 之外，并能给客户团队立起基本的分支和 MR 规范

## 结语

核心工程能力不性感，练的都是基本功。但驻场工程师的职业声誉，就是在一次次「这个问题我能现场解决」中攒起来的——SQL 写得快，原型出得快，系统部署得上去，出了问题查得出来。

这一支柱是底座，但光有底座只是「能干活」。怎么在模糊需求里找到真正的问题、怎么跟客户的多方干系人打交道，是后续支柱要展开的内容。系列总览和其余五大支柱见主文：[FDE 技能栈全景图](./2026-09-14-fde-skill-stack-pillar.md)。
