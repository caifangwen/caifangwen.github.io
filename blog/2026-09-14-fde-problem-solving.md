# FDE 技能栈深入（二）：问题求解能力——在模糊与混乱中交付答案

> 本文是《FDE 技能栈全景图》系列的第二篇，深入展开「问题求解能力」这一支柱。系列主文见 [FDE 技能栈全景图](./2026-09-14-fde-skill-stack-pillar.md)。

## 为什么把问题求解单独列为一个支柱

先说一个现场的真实场景。

你刚到客户现场第一周，业务方的负责人把你拉到会议室，在白板上写了四个字：「数据中台」。然后他说：「我们领导看了华为的分享，觉得我们也要搞一个，你们 Palantir 系的方法论不是很厉害吗，三个月能上线吧？」

如果你是一名普通的后端工程师，这个场景不属于你——会有产品经理把需求写成 PRD，会有架构师画好方案，你拿到的是边界清晰的任务。但你是 FDE，现场没有别人。从「数据中台」这四个字到三个月后可运行的系统，中间所有的空白都要你来填：他到底想解决什么问题？数据在哪、脏到什么程度？三个月里先做什么、不做什么？每一步怎么验证方向没跑偏？

这就是问题求解能力要回答的问题。它包含三个子能力：

- **需求挖掘与问题定义**：把客户说出口的「解决方案」还原成真实的「问题」；
- **快速原型与迭代**：用最便宜的方式验证方向，而不是赌上两周工期；
- **模糊环境下的拆解**：把宏大命题切成可交付、可验收的小块，并管理不确定性。

支柱一（核心工程能力）决定你「能不能做出来」，支柱二决定你「做的是不是对的东西」。FDE 的绩效不看你写了多少代码，看你解决了多少问题——方向错了，工程能力越强，浪费越大。

下面逐节展开。

---

## 一、需求挖掘与问题定义

### 1.1 是什么：区分「说的需求」和「真的问题」

客户几乎从不直接描述问题，他们描述的是自己想象出来的解决方案。「我要一个报表系统」「我要一个 AI 问答机器人」「我要把数据打通」——这些都是方案，不是问题。方案背后是问题，问题背后是人，人背后是利益和考核。

需求挖掘就是逆向工程：从客户给出的方案，倒推出真实的问题、真实的用户、真实的约束。

### 1.2 为什么：做错的需求是最贵的需求

驻场项目最贵的成本不是服务器也不是人力，而是**返工**。一个做错的模块，代价不只是开发它的两周，还有客户信任的损耗——客户一旦形成「他们做的东西不是我们要的」的印象，后面每一步都会变得困难。

反过来，问题定义清楚了，解决方案往往是平庸的、显而易见的。FDE 圈里有句老话：**一个定义清楚的问题，已经解决了一半**。

### 1.3 怎么做

#### 方法一：5 Why 追问（配合复述确认）

5 Why 不是机械地问五次「为什么」，而是沿着因果链往下挖，直到挖到「可行动」的层面。示例：

> 客户：我要一个销售报表系统。
>
> - 为什么需要报表系统？—— 现在数据散落在各地市公司的 Excel 里，汇总慢。
> - 为什么慢是问题？—— 每周经营分析会要用，现在周三才能凑齐上周数据。
> - 为什么必须周三前拿到？—— 周三是集团例会，大区总要在会上被点名。
> - 点名的压力在哪？—— 主要看三个指标：回款率、库存周转、大单进度。
> - 现在有这三个指标的人是谁？—— 大区总助理，每周二晚上手工拼 Excel 到凌晨。

挖到这里，真实需求浮现了：**不是「报表系统」，而是「让大区总助理在周二下午五点前拿到三个指标」**。最小方案可能根本不是系统，而是一条定时跑的数据管道加一张自动刷新的看板。

注意两点：

- 追问的语气是「我想理解你们的处境」，不是审问。每问一两层，把你理解的内容复述一遍让对方确认：「我理解一下，核心痛点是周二晚上拼数据这件事，对吗？」
- 挖到「可行动层」就停：你能直接对「周二下午五点前产出三个指标」采取行动，但对「大区总要面子」无法直接行动。挖到利益层是为了理解动机，方案落点还是要在可行动层。

#### 方法二：现场观察（Shadowing），区分「说的」和「做的」

访谈里客户描述的流程，和实际发生的流程，几乎总是有偏差的。这不是客户撒谎，而是人对自己工作的描述天然会省略「习以为常的部分」，而那些部分往往才是关键。

做法很简单：**申请跟着一线用户坐半天**。看那个周二晚上拼 Excel 的助理实际操作一次。你会看到：

- 她的数据源不是两个，是七个，其中三个要靠微信找人要；
- 某个系统的导出功能每天下午四点后必超时，所以她都是早上先导出存着；
- 她手工处理的「技巧」——比如把两类编码用 VLOOKUP 对上——这套映射逻辑没有任何文档，只存在于她的脑子里和她的 Excel 里。

这些东西，你开十次访谈会都问不出来，但看一次操作全都能看到。而她脑子里的那套映射表，就是你数据管道里 join 逻辑的真相。

实操建议：观察时少说话，多问「这一步为什么要这么做」，把每一步用到的系统、文件、联系人记下来，回去当天画成一张现状流程图（as-is），拿去和客户确认。这张图本身就是第一个交付物。

#### 方法三：问题重述——把「方案」翻译成「问题」

每当你听到一个以「我要一个 XX 系统 / XX 功能」开头的需求，强制自己做一次翻译：

| 客户说的（方案） | 翻译后的问题定义 |
|---|---|
| 我要一个报表系统 | 谁在什么时间需要看什么数据做什么决策？现在怎么拿到的，慢/错在哪？ |
| 我要 AI 问答机器人 | 谁在回答重复性问题？这些问题有没有标准答案库？答错的代价是什么？ |
| 我要把数据打通 | 哪个具体业务动作因为数据不通而做不了？打通哪两张表能解决 80%？ |

翻译不出来的需求，说明信息还不够，回去继续挖，不要动手。

#### 输出物：一页纸问题定义（Problem Statement）

挖掘完成后，把所有结论收敛到一页纸，发给客户方所有干系人确认。模板：

```
# 问题定义：XXX

## 背景与现状
谁（具体角色，不是"业务部门"这种笼统称呼），在什么场景下，
目前通过什么方式完成什么任务。

## 痛点
现状方式的具体问题：耗时多少、错误率多少、造成了什么后果（尽量量化）。

## 目标状态
什么角色在什么时间点能拿到什么结果，用什么指标衡量"变好了"。

## 范围外（本期不做）
明确列出不做什么——这一条和"做什么"同样重要。

## 关键约束
数据权限、网络环境、审批流程、时间节点。

## 成功标准
可验收的具体条件，例如"周二 17:00 前三个指标自动刷新，与手工结果误差为 0"。
```

这页纸的价值有三个：对齐认知（客户确认「你们理解对了」）、划定边界（防止范围蔓延）、验收依据（三个月后撕不掉的标准）。**发出去、收到书面确认，才算问题定义完成。**口头说「对对对就是这样」不算数。

### 1.4 常见坑

- **只访谈领导，不接触一线**。领导说的是他想让流程成为的样子，一线做的才是流程真实的样子。两类人都要聊，但动手前以一线为准。
- **把客户的方案当需求接进来**。客户说「加个审批流」，你接了，做完发现他真正要的是「出了问题能找到责任人」——一个操作日志字段就能解决。永远先翻译再承接。
- **问题定义写得太大**。「提升供应链效率」不是问题定义，是口号。检验标准：如果三个月后你无法判断这个问题是否被解决了，说明定义不够具体。
- **跳过书面确认**。现场节奏快，很多人觉得「聊清楚了就行」。项目中期干系人更换、记忆出现分歧时，那一页纸是你唯一的锚。

## 二、快速原型与迭代

### 2.1 是什么

用尽可能低的成本、尽可能短的时间，做出一个**能被客户看到、摸到、给出真实反馈**的东西，然后根据反馈快速修正。原型的目的不是展示进度，而是**澄清需求和验证假设**——它是需求挖掘的延续，是你在问客户：「是这个意思吗？」

### 2.2 为什么：现场的需求永远模糊，原型是最好的澄清工具

人对抽象描述的反馈质量极低。「你要的报表是 A 样式还是 B 样式？」客户说都行。你把两个都画出来放他面前，他立刻会说「A 好，但这个数字要标红，我们领导只看红的」。

文字需求文档让客户确认的是「你以为他说了什么」，原型让客户确认的是「他自己到底要什么」。驻场项目里，原型的迭代速度以「天」为单位：今天演示，今晚改，明天再看。这个节奏本身就是竞争力——客户内部 IT 一个需求排期两个月，你第二天就拿出了能点的东西，信任就是这么建立的。

另外一层原因更现实：**控制试错成本**。48 小时做出来的东西方向错了，损失两天；闷头开发两周再演示，方向错了就是灾难。

### 2.3 怎么做

#### 48 小时原型的工作流

1. **第 0 步：确定原型要验证的假设**。一个原型只验证一件事。「验证这三个指标的计算口径对不对」和「验证这个交互业务方能不能用明白」是两个原型，别混着做。
2. **第 1 步：选最快的工具，不是最好的工具**。标准只有一个：你对它最熟、出活最快。
3. **第 2 步：用真实数据，哪怕是脏的**。拿假数据演示，客户的反馈全是「数据不对」，浪费一次反馈机会。宁可只接一张表的真实数据。
4. **第 3 步：演示，记录反馈，当场确认优先级**。反馈要逐条记下来，当场和对方确认「这三条里哪个最痛」。
5. **第 4 步：当天或次日迭代，再演示**。循环，直到客户说「就是它了」——这时候你才真正开始工程化开发。

#### 原型工具箱（按场景选）

- **数据分析/口径验证类**：Jupyter Notebook + pandas。直接在客户面前改代码、重跑 cell，「你说这个口径不对，那我改一下，你看现在的数对不对」——这种现场感是任何 PPT 给不了的。
- **交互界面类**：Streamlit（Python）或 Gradio。几十行代码出一个带筛选、图表、表格的 Web 应用：

```python
import streamlit as st
import pandas as pd

st.title("大区经营指标看板（原型 v0.1）")

df = pd.read_csv("metrics.csv")  # 真实数据，哪怕只接了一张表
region = st.selectbox("选择大区", df["region"].unique())
kpi = df[df["region"] == region]

col1, col2, col3 = st.columns(3)
col1.metric("回款率", f"{kpi['repay_rate'].iloc[0]:.1%}")
col2.metric("库存周转天数", f"{kpi['inv_days'].iloc[0]:.0f} 天")
col3.metric("在途大单数", f"{kpi['big_deals'].iloc[0]}")

st.line_chart(kpi[["repay_rate", "inv_days"]])
```

  半小时能交付给客户一个能点的东西。客户内网部署不了就本地跑 + 屏幕共享，演示阶段不要提前背上部署包袱。
- **流程/报表样式类**：Figma 或直接 Excel 画 mock。验证「领导要的样式」时，一张图比代码更快。
- **数据管道类**：不要为原型搭 Airflow。一个能手动跑的 Python 脚本 + cron 就够了，调度是工程化阶段的事。

#### 砍需求：MVP 的刀法

客户看原型时一定会加需求。「能不能再加个导出」「能不能按部门下钻」。应对方式不是拒绝，而是**公开排期**：维护一张所有人可见的需求清单，新需求一律进清单，和客户一起排优先级。砍需求的依据始终回到问题定义那一页纸：「这个需求服务于我们定义的哪个痛点？」对不上的，往后排。

### 2.4 常见坑

- **把原型当产品做**。给原型写单元测试、做权限系统、纠结代码结构——全错。原型的宿命是被扔掉或被重写，它唯一的 KPI 是「多快拿到反馈」。
- **舍不得扔原型**。反过来，验证了方向之后，很多人直接把原型代码续成正式系统，Streamlit 脚本长成几千行的怪物。原型验证完成后，该用正经技术栈重写就重写，原型里的业务知识（口径、映射、规则）才是要带走的东西。
- **用假数据演示**。上文说过，再说一遍：假数据换来假反馈。
- **演示没有 Plan B**。客户现场网络、投屏、权限随时会翻车。每次演示前准备：录屏视频 + 本地可离线运行的副本。现场翻车时淡定切换，反而加分。
- **反馈不记录、不确认**。口头反馈三天后双方记忆必然不一致。每次演示后把反馈清单发群里或邮件确认，这同时也在向客户展示你的迭代速度。

## 三、模糊环境下的拆解能力

### 3.1 是什么

客户给的命题往往是「搞个数据中台」「用 AI 提升质检水平」这种级别。拆解能力就是把这种宏大、模糊的命题，切成一连串**两周内可交付、交付后客户能验收**的小块，并排出顺序。

### 3.2 为什么

驻场项目有两个死法：一种是憋大招，三个月不见东西，客户耐心耗尽；另一种是东一榔头西一棒子，每周都很忙，三个月后拼不出一个完整的东西。拆解就是为了避开这两种死法：**每周都有可见的进展，且所有进展指向同一个终点。**

### 3.3 怎么做

#### 第一步：画出「端到端骨架」

面对宏大命题，先强迫自己画出从数据源头到用户拿到结果的完整链路。拿「数据中台」来说，和客户一起确认出的最小骨架可能是：

```
业务系统 A/B/C → 数据接入 → 清洗整合 → 三张核心主题表 → 一个经营看板
```

骨架的意义是**划定边界**：中台可以有一万件事，但本期只做这一条链路上的事。骨架上每个环节都是一个工作包。

#### 第二步：找关键路径——先解开「解锁点」

不是所有工作包价值相等。问自己：**哪一件事做完，能解锁后面最多的事？哪一件事风险最大、不确定性最高？**通常答案是同一件，而它应该排在最前面。

驻场项目里最典型的解锁点是**数据接入**。客户的系统能不能连、权限批不批得下来、数据质量烂到什么程度——这些事不验证，后面所有排期都是空中楼阁。所以拆解的第一条铁律：**第一周就去摸数据**。哪怕只是用 SQL 连上库跑几个探查查询：

```sql
-- 表量级与时间范围
SELECT min(create_time), max(create_time), count(*) FROM orders;

-- 关键字段空值率（脏数据摸底）
SELECT
  round(100.0 * sum(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END) / count(*), 2) AS null_customer_pct,
  round(100.0 * sum(CASE WHEN amount IS NULL THEN 1 ELSE 0 END) / count(*), 2) AS null_amount_pct
FROM orders;

-- 编码值分布（发现"其他/未知/-1"这类脏值）
SELECT status, count(*) FROM orders GROUP BY status ORDER BY count(*) DESC;
```

这几个查询跑完，你对项目真实难度的判断会超过开十次会。数据质量探查的完整方法在支柱一的数据工程篇展开，这里只强调它在拆解中的位置：**它是所有排期的前置条件**。

#### 第三步：按「可验收」切成两周迭代

每个迭代必须满足：有明确的产出物、客户方有人能验收、验收标准和问题定义页里的成功标准能挂上钩。一个反例是「完成数据清洗模块开发」——客户无法验收，只能你说完成了。改成「大区经营看板上三个指标自动刷新，与手工核对误差为 0」——这才是可验收的。

经验法则：切到两周还切不动的块，说明你对它理解不够，先安排一个「技术预研/数据摸底」的小迭代去理解它，而不是硬着头皮排工期。

#### 第四步：管理不确定性——坦诚比自信值钱

模糊环境里一定有答不上来的问题。客户的领导问「三个月能不能上线」，错误答案是拍胸脯，正确答案是结构化地管理预期：

- 「接入 A、B 两个系统的部分，我们摸过数据了，有把握，六周。」
- 「C 系统的数据权限还在等审批，这是最大的风险点，下周三前我们给出明确结论。」
- 「如果 C 赶不上，我们先上 A+B 的版本，C 作为第二期——这是降级方案。」

坏消息早报、给出降级路径，这是专业；打包票然后翻车，这是事故。客户见得多了，分得清这两种人。

### 3.4 常见坑

- **按技术模块拆，而不是按可验收结果拆**。「先做数据层、再做服务层、再做前端」拆出来的是三个没法演示的中间态。按「端到端薄片」（先打通最小链路，再逐层加厚）拆，每周都有东西给客户看。
- **低估客户的流程性延迟**。数据权限审批、安全评估、网络开通，这些在客户组织内动辄以周计。拆解时把它们作为显式任务列出来、明确责任人是客户方的谁，而不是默认「到时候自然会有」。
- **拆完就僵死执行**。拆解是假设，每周要根据实际进展重排。固定的不是排期表，是问题定义页上的成功标准。
- **同时开多条战线**。现场人手有限（常常只有你一个），并行三条线等于三条线都延期。串行做完一个可验收的迭代，胜过三个半成品。

## 四、学习路径建议

问题求解能力没有对应的认证考试，只能靠刻意练习加实战。一个可执行的路径：

**第 1-2 个月：练提问和定义**

- 读《你的灯亮着吗？》（*Are Your Lights On?*）——问题定义领域的经典小册子，一两天能读完；
- 在日常工作中强制练习：接到的每一个需求，先写一页纸问题定义再动手，哪怕是内部需求；
- 把你经手过的项目翻出来做复盘：当时定义的问题，和后来发现的真实问题，偏差在哪。

**第 3-4 个月：练原型速度**

- 把 Streamlit 练到「不看文档半小时出一个带图表的看板」的程度；
- 给自己限时训练：随便找一个公开数据集，限定 4 小时做出一个能演示的东西，练习「砍」的手感；
- 练习演示：给同事讲你的原型，训练三分钟讲清「这是什么、解决什么、下一步是什么」。

**第 5-6 个月：练拆解**

- 拿一个你熟悉的系统，假装它是客户给的模糊命题，练习画端到端骨架、找关键路径、切成两周迭代；
- 学习基础的项目风险管理（不需要考 PMP，能维护一张风险清单即可：风险、概率、影响、应对、责任人）。

**长期：建立复盘习惯。**每个项目结束时回答三个问题：最初的问题定义准不准？原型阶段哪次反馈改变了方向？拆解的排期和实际偏差多大、为什么？问题求解能力的成长几乎全靠复盘喂出来。

---

## 五、自测清单

动手接一个新需求前，对照检查：

- [ ] 我能用自己的话复述客户的问题，并且客户确认过我的复述？
- [ ] 我区分开了客户要的「方案」和背后的「问题」？
- [ ] 我接触过真正的一线用户，而不只是听管理层转述？
- [ ] 我有一页纸的问题定义，且有客户的书面确认？
- [ ] 问题定义里明确写了「本期不做什么」？
- [ ] 成功标准是可验收的（半年后任何人都能判断做没做到）？
- [ ] 我的第一个原型能在 48 小时内拿出来，且用的是真实数据？
- [ ] 原型只验证一个明确的假设，而不是「先做个大概」？
- [ ] 每次演示的反馈都有记录并经客户确认？
- [ ] 我的拆解是按「可验收结果」切的，不是按技术模块切的？
- [ ] 数据接入和数据质量摸底被安排在了第一周？
- [ ] 我对不确定的部分给出了明确的时间点和降级方案，而不是打包票？

---

## 结语

问题求解能力的内核只有一句话：**先确保做对的事，再确保把事做对**——前者靠定义清楚问题，后者靠原型和拆解控制试错的成本与节奏。工程能力决定你能走多快，问题求解能力决定你走的方向值不值得。
