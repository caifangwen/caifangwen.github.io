# FDE 产品思维之优先级判断：十个需求砸过来时，你凭什么排序

> 系列三级专题 · 对应《FDE 技能栈之产品思维》的「优先级判断」一节。父级文章讲了排序的三维框架（价值 × 成本 × 战略意义）、砍需求的三个过滤器和说"不"的基本模板；本文往下钻一层：需求进来时的分诊流程、打分怎么校准、产能怎么算、排序会议怎么开、以及优先级动态变化时怎么处理。

## 一个典型的周二上午

驻场第三个月，某制造企业客户。周二上午十点半，你的待办清单长这样：

- 生产总监昨天在群里 @ 你：月底集团领导来视察，"数据大屏能不能搞一个"，语气是不容商量的。
- 质检科长上周提的"不良品追溯报表"已经催了第二次，说再不出数她这个月考核没法做。
- 一线班长在车间拉住你：现在的录入界面要填 12 个字段，"能不能就扫个码自动带出来"。
- 客户 IT 部门发邮件：你们的系统日志必须接入他们的审计平台，"这是合规要求，月底前完成"。
- 自己公司的产品团队：新做的规则引擎模块想找个现场试点，"你这个客户正合适"。
- 你手上还有一个做了一半的主线任务：报警数据管道的二期改造，原计划周五交付。

六件事，每件提的人都觉得最急。你一周的真实可用工时大约 30 个小时，满打满算能交付两件半。**怎么选、怎么砍、怎么跟被砍的人交代——这就是优先级判断，也是本文要解决的全部问题。**

父级文章给过框架了，这里先把结论放前面：优先级判断不是一门"打分"的学问，而是一套**从需求进门到交付承诺的流水线**——分诊、估容量、排序、承诺、重排，每个环节都有具体做法。打分只是其中一个环节。

## 一、需求分诊：不是所有"需求"都配进入排序

### 是什么

大多数人做优先级排序的第一步就错了：把所有涌过来的事直接扔进一个列表开始排。结果是列表越排越长，因为里面混着三种完全不同的东西：**真正的问题、包装成需求的解决方案、以及别人转嫁过来的工作**。分诊（triage）的目的就是在排序之前把它们区分开，该澄清的澄清、该拦截的拦截、该转走的转走。

### 怎么做：建一条需求流水线

现场不需要重型工具，一张表就够——GitHub Projects、飞书多维表格、甚至一个共享 Excel 都行。关键是每个进来的需求先过三个状态，而不是直接进 backlog：

```
收件箱（Inbox）→ 澄清中（Clarifying）→ 已分诊（Triaged）→ 排期中（Scheduled）
                                        ↘ 已拒绝/转交（Declined/Referred）
```

每个需求在收件箱里先填一张最小卡片，五个字段：

```yaml
# inbox/017-质量追溯报表.yaml
title: 不良品追溯报表
requester: 质检科-王科长           # 谁提的
stated_want: 做一个追溯查询页面    # 他说的"要什么"
real_problem: 待澄清               # 他要解决什么问题（关键字段）
deadline_claimed: "本月底"         # 声称的期限
deadline_real: 待核实              # 真实期限（同样关键）
```

`real_problem` 和 `deadline_real` 是分诊的核心动作。`stated_want` 是客户给的解决方案，你要往回翻译一层：王科长要追溯页面，真实问题可能是"月底考核需要按供应商统计不良率"——如果是这样，一条 SQL 加一张定时邮件报表今天就能解决，根本不需要页面。期限也一样："月底前"要追问"月底发生什么"，集团视察的 deadline 是真的（领导行程不会为你改），考核 deadline 也可能是真的，但"尽快""越快越好"不是期限。

澄清手段就两种，成本都很低：五分钟当面对话，或者去现场看十分钟他现在的操作流程。需求挖掘的完整方法在支柱二的专题里，这里只强调一点：**没填出 `real_problem` 的需求不允许进入排序环节**。这一条能挡掉收件箱里三到四成的条目。

### 常见坑

- **把"领导说的"当成需求本身。** 领导说"搞个大屏"，这不是需求，是指示。分诊动作是去找领导或他身边的中层问清楚：视察时要展示什么、给谁看、希望对方看完记住什么。问完你会发现，要的可能是"三条核心产线的实时产量和良品率"，一个 Metabase 看板就能扛住，而不是价值三十万的可视化大屏项目。
- **合规需求不过滤直接接。** IT 部门的"日志接入审计平台"听起来没有商量余地，但合规需求恰恰最要分诊：找他们要审计平台的数据接入规范文档，看清楚要求的到底是"全量实时接入"还是"关键操作日志按月导出"。两者的成本差一个数量级。**合规要求必须满足，但满足的方式有谈判空间。**

## 二、估产能：排序的分母是多少

### 是什么

排序是"需求 ÷ 产能"的游戏。大多数人只琢磨分子（需求怎么排），从来不量分母（自己到底有多少时间）。驻场 FDE 的名义工时是每周 40 小时，真实可用工时通常只有一半多一点——剩下的被会议、现场救火、客户临时召唤、干系人沟通吃掉了。分母算错，排出来的计划从第一天起就是废纸。

### 怎么做：先量两周，再定规矩

**第一步：测真实产能。** 连续两周，每天下班前花两分钟记录当天时间分布，只分三桶：

```
2026-09-07（周一）
- 深度开发（写代码/搭管道/调模型）: 3.5h
- 沟通协作（会议/演示/对齐/客户临时找）: 3h
- 救火与杂务（线上问题/环境故障/权限审批跑腿）: 2h
```

两周后你会得到一个自己的数字。驻场环境的典型分布是深度开发只占 40%-50%，也就是每周 16-20 小时。这个数字就是你排期的分母，按它算：**一个估 5 人日的任务，在你的日历上意味着两周**，不是一周。

**第二步：固定资源配比。** 把可用工时按桶预先切分，而不是来了需求再抢：

| 桶 | 占比 | 装什么 |
|----|------|--------|
| 主线交付 | 60% | 当前迭代承诺的一到两件事，雷打不动 |
| 干系人响应 | 25% | 各路人马提的小需求、查询支持、演示准备 |
| 救火与机动 | 15% | 线上故障、突发检查、领导临时要的东西 |

配比的价值在于**让拒绝有据可依**。"我这个月的主线容量已经承诺给报警管道二期了，你的需求排进机动队列，预计两周后能做"——这不是推诿，是透明的产能管理。而且桶是硬的：主线桶被领导临时需求挤占时，要当面说清楚代价："可以，那管道二期顺延一周，周五的交付改成下下周三，您确认一下。"大多数临时需求听到这句话会自动降级。

**第三步：估算用"人日"且只分三档。** 现场不需要 Fibonacci 点数那套，三档足够：小事（≤1 人日）、中事（2-5 人日）、大事（>5 人日）。**大事一律先拆再排**——任何超过五天的任务说明你没想清楚，拆成能独立交付的小块再进排序。这也是对"48 小时出原型"原则的呼应：拆到每块都能在一两天内给客户看点东西。

### 常见坑

- **按 100% 产能排期。** 把 30 小时全排满，第一次现场救火就全盘崩。上面的桶里已经留了 15% 机动，别再吃它。
- **估算时不含联调和等待。** 驻场开发的最大时间黑洞不是写代码，是等：等客户 IT 开权限、等接口人回复、等审批流程。估算涉及外部依赖的任务，工期按"开发时间 × 2"起步。

## 三、排序：打分模型的实操与校准

### 是什么

父级文章给了三维打分框架（业务价值 × 实现成本 × 战略意义），以及它的真正作用——把判断显性化，让分歧变成对具体分数的争论。这一节解决父级没展开的实操问题：分数怎么校准、多个人打分怎么合并、模型什么时候该被推翻。

### 怎么做

**先校准锚点，再打分。** 1-5 分空着定义就是各打各的。给每一维定具体锚点，例如业务价值：

```
5分 = 直接影响客户方拍板领导的核心 KPI，或消除一个正在流血的痛点（每天发生、有人因此加班）
4分 = 显著改善某部门的核心流程，有可量化的工时或错误率收益
3分 = 改善明显但范围有限，或受益方是中层而非决策层
2分 = 体验优化类，好用但不是痛点
1分 = nice to have，没人会因为没做而受损
```

成本维和战略维同理。把锚点表放在打分表旁边，团队打分的一致性会立刻提升——你和客户方负责人对同一需求的打分差从平均 2 分收敛到 1 分以内，这不是小事，因为差 2 分的表排不出共识，差 1 分的可以。

**用加权而非简单相加。** 三维的权重不是等价的。FDE 现场的经验配比是价值 50%、成本 30%、战略 20%——现场首先是交付价值的地方，产品化是加分项不是主目标。写个小脚本固化计算，比每次心算可靠，也方便调权重做敏感性测试：

```python
# score.py —— 输入 backlog CSV，输出加权排序
import csv

W_VALUE, W_COST, W_STRATEGY = 0.5, 0.3, 0.2

def score(row):
    return (W_VALUE * int(row["value"])
            + W_COST * int(row["cost"])       # cost 分高 = 便宜
            + W_STRATEGY * int(row["strategy"]))

with open("backlog.csv") as f:
    items = sorted(csv.DictReader(f), key=score, reverse=True)

for rank, it in enumerate(items, 1):
    print(f'{rank:2d}. [{score(it):.1f}] {it["title"]} '
          f'({it["size"]}, requester: {it["requester"]})')
```

backlog.csv 的格式就是分诊环节那张表加上三个分数和规模档位，一个文件从进门管到排期。

**设两个模型之外的 override 规则。** 模型是辅助，有两种情况必须允许推翻排序，但要写成显式规则，而不是每次临时纠结：

1. ** unblock 优先**：如果一件低分小事卡着一件高分大事（比如"拿到 X 系统的只读账号"卡着整个数据管道），小事无条件提前。
2. **信任存款**：对还没建立信任的新干系人，第一件需求只要不离谱就优先做——这是在存信任，后续你说"不"的时候才有信用额度。但同一人的第二件需求回归正常排序。

**多人打分取"分歧优先讨论"。** 排序会上逐条念分数是浪费时间。正确姿势：会前各自离线打分，会上只讨论标准差大于 1 的条目——你们对某条需求的价值一个打 2 一个打 5，这背后是信息不对称（他知道月底考核的压力你不知道，或者你知道接口不稳定他不知道），聊十分钟把信息对齐，分数自然收敛。分数一致的条目直接过。

### 常见坑

- **打分精确到小数点，制造虚假的客观。** 三维各 1-5 分加权出来的 3.4 和 3.6 没有区别，别为了 0.2 分争半小时。分数的意义是把需求分进"必做/可做/不做"三个档，不是排出唯一的全局次序。
- **战略意义维度被滥用。** "这个以后能产品化"是给自己加戏的重灾区。检验标准和父级的"三次原则"一致：说不出第二个具体会用到它的客户或场景，战略分不许超过 2。
- **模型算完不回头看。** 每月花十五分钟复盘：上个月排第一的事，交付后的实际价值和预估分匹配吗？连续三个月价值分高估的，说明你的锚点表飘了，调。模型不校准会贬值。

## 四、排序会议：让排序权变成共识而不是对抗

### 是什么

父级文章提了"每周 30 分钟、拉客户方核心干系人一起过 backlog"。这一节把会怎么开讲细，因为**这是优先级判断里政治含量最高的环节**：你的目标不是宣布排序结果，而是让客户方的人自己参与排出这个序——他们排出来的序，才会认账；你单方面宣布的序，每条都是未来扯皮的伏笔。

### 怎么做：30 分钟议程

会前准备（10 分钟）：跑一遍打分脚本得到建议排序，标出与上周相比的变动项和新进条目，发预读。

```
00:00-00:05  上周交付回顾：承诺了什么、兑现了什么（先立信用）
00:05-00:10  产能同步：本周可用桶、救火占用了多少、主线进度
00:10-00:20  过变动项：新需求分诊结果、分数有分歧的条目逐条对齐
00:20-00:28  确认本周承诺清单：白纸黑字，谁提的需求排了第几
00:28-00:30  被拒绝/挂起项的复述：确保被砍的人知道自己被砍了、为什么
```

三个细节决定这个会的成败：

- **让干系人互相PK，而不是和你PK。** 质检科长和生产总监同时争机动桶的名额时，把问题抛回给他们："机动桶这周只有 4 个小时，两件只能做一件，两位看哪个更急？"你把稀缺的约束摆出来，他们自己会做政治权衡，而且结论是他们做的，不是你给的。
- **承诺清单发书面纪要。** 会后一封邮件或群消息："本周承诺：1) 报警管道二期周五交付；2) 质检追溯报表（SQL+邮件版）周三出。挂起：大屏方案待视察目标确认后进排期。"文字记录是你三个月后对上扯皮的唯一武器。
- **被砍的人必须当场听到理由和出口。** 出口就是替代方案（父级文章的说不模板）或者明确的重估时间点（"视察结束后第一周重新评估"）。没有出口的拒绝会变成怨气，有出口的拒绝只是延期。

### 常见坑

- **只叫提需求的人，不叫能拍板的人。** 如果客户方没有一个能仲裁优先级冲突的角色参会，会议产出的是"愿望清单合并"而不是排序。会前先确认：谁是客户方的 single owner？没有的话，推动他们指定一个——这本身也是交付的一部分。
- **会议变成进度汇报会。** 进度用书面同步，会议时间只花在分歧和取舍上。守不住这条，30 分钟会变成 90 分钟，然后大家开始找借口不来。

## 五、动态重排：优先级不是定出来的，是维护出来的

### 是什么

父级文章提醒过"优先级只定一次"是坑。这一节讲机制：什么事件触发重排、重排怎么控制成本、怎么区分"真变化"和"应激反应"。

### 怎么做

**列一张触发事件清单，其余一律走下周例会。** 驻场现场值得立即重排的事件其实就那么几类：

- 客户组织架构或关键人变动（新领导上任必然带来新优先级，主动约聊而不是等他发难）
- 生产事故或安全事件（救火期间主线自动冻结，事后明确恢复时间点）
- 上级单位的临时检查/视察（硬 deadline，提前重排）
- 外部依赖状态变化（接口突然可用/突然下线、数据权限批了/被收回）

除此之外的需求变化，一律回复"已记录，周四排序会上过"。**把重排的决策点收敛到固定的会议，是防止优先级被每天的噪音拖着走的唯一办法。**

**区分真变化和应激反应，用两周冷却期。** 父级文章的三过滤器里有"两周后它还重要吗"，执行层面加一个具体动作：给 backlog 里每个非触发事件类的新条目打上 `cooling_until` 日期（提出日 + 14 天），脚本过滤展示时默认隐藏未到期的条目。两周后还在被提起的，自动浮出水面。你会惊讶于冷却队列的自然死亡率——现场大概一半的"急事"活不过两周。

**重排要收"切换费"。** 每次中途打断主线任务，当面对提出者说清楚代价："现在切过去，管道二期损失的不只是今天这半天——重新进入上下文还要再花半天，总代价一天，周五交付顺延到下周一。确认要切吗？"这不是赌气，是让打断的成本显性化。大多数"紧急需求"在成本明码标价之后会发现其实可以等。

### 常见坑

- **重排不通知受影响的人。** 排序变了，被顺延的需求方必须当天知道。主动同步一句"你的报表因集团视察需求顺延到下周三"的成本是一分钟；等他自己来问时，你要花十分钟修复信任。
- **主线任务频繁让位，最后永远交不了。** 连续两周主线被临时需求打断超过 30%，说明不是优先级问题，是承诺机制失效——该升级了：拉上双方管理层，把主线交付的政治价值讲清楚，给主线争取"豁免权"。

## 六、说不的进阶场景

父级文章给了说不的结构（承认诉求 → 给出代价 → 替代方案 → 交回选择权）。补三个父级没覆盖的高难度场景：

**对拍板领导说不（或说"换个方式做"）。** 对最高权力者不硬顶，但也不全接。武器是"范围谈判"而不是"接或不接"：大屏项目全量做要六周赶不上视察，但"三条核心产线、六个指标、静态数据兜底"的版本一周能出。**给领导的不是 yes/no，是三个档位和三档交付日期，让他在知情状态下选。** 他选了精简版，你的产能保住了；他选了全量版，延期是他签字的决定。

**对"自己人"说不。** 总部产品团队要试点新模块，这类需求最难拒——拒绝成本是内部政治成本。处理方式是把它正常走分诊和打分，然后把分数透明地摆出来："试点进排序后是第五名，前面的四件是这些。如果你认为试点应该插队，帮我说服客户方把哪件挪出来。"把内部需求的插队成本转嫁回给提出者，而不是自己消化。

**对已承诺的事说不（砍自己）。** 最难的拒绝是砍自己排过期的承诺。信号是：任务进行中，前提条件消失了（需求方调岗了、数据源头系统要下线了、视察取消了）。这时候沉没成本会拖着你把它做完——别做。**优先级判断的对象不只是新需求，也包括进行中的工作。** 每周末问一次：手上这件事如果今天才提出来，还会排这个名次吗？不会的话，降级或砍掉，并向干系人说明。砍自己砍得干脆的 FDE，说的话才有分量。

## 练习与自测

### 练习方法

1. **历史回放（一人可练）。** 翻出你过去三个月实际接到的需求清单（聊天记录、邮件、工单），用本文的流水线重新走一遍：分诊填卡、三档估算、锚点打分、加权排序。对比你当初的实际处理顺序，统计：有多少需求其实该被过滤器拦下？排序差异最大的三条，差异原因是什么？这个练习成本一个下午，暴露的盲区比读十篇文章多。
2. **产能实测（两周）。** 按第二节的方法记录两周时间分布，得出自己的深度开发占比。低于 40% 的，先解决环境问题（会议太多？响应通道太杂？）再谈排序技巧——分母出问题，分子排得再漂亮也没用。
3. **模拟排序会（最好三人）。** 找两个同事扮演"催命的中层"和"要试点的内部产品"，你主持一次 30 分钟排序会，用真实 backlog。练两个具体动作：把互相争抢的需求抛回给他们 PK、给每个被砍项说出出口。录下来回看，数自己说了几次"做不了"以外的句式。
4. **每周一封承诺纪要。** 从今天起，每周排序后发一封五行的书面同步（承诺什么、挂起什么、顺延什么、为什么）。坚持八周，你会直观感受到扯皮量的下降。

### 自测标准

- [ ] 我的收件箱里每个需求都能说出 `real_problem` 和 `deadline_real`，说不出来的没进排序
- [ ] 我报得出自己每周真实的深度开发小时数，且排期按它算
- [ ] 我的工时有显式配比（主线/响应/机动），挤占主线时我会当面对齐代价
- [ ] 打分有写下来的锚点定义，不是我每次凭感觉拍
- [ ] 排序会有客户方能拍板的人参加，产出书面承诺清单
- [ ] backlog 里有冷却期机制，我能说出上个月自然死亡的需求有几条
- [ ] 中途打断我主线的事，我每次都明码标价了切换成本
- [ ] 最近一个月我砍过自己已承诺的一件事，并向干系人主动说明
- [ ] 我给领导的需求提供过档位选择，而不是简单的接或拒
- [ ] 上个月的排序结果我做过复盘，校准过打分锚点

## 结语

优先级判断的尽头不是一张排得漂亮的表，而是两样东西：**你承诺的都兑现了，你拒绝的都给了出口。** 做到这两点的 FDE，客户会把"什么该做"的决定权也慢慢交给你——那是这个岗位能拿到的最高信任。
