# FDE 技能栈（五）：交付与项目管理——现场没有 PM，你就是 PM

> 系列子文章 · 支柱五：交付与项目管理。本文是 [FDE 技能栈全景图](./2026-09-14-fde-skill-stack-pillar.md) 中「交付与项目管理」一章的深入展开。

## 为什么这一支柱重要

在大厂做工程师，你的交付链路是被层层托底的：PM 盯排期，QA 把质量，SRE 管上线，安全团队做合规评审。而在客户现场，这些角色往往一个都不存在——FDE 常常是现场唯一的工程师，一个人要同时是开发、测试、运维、PM 和安全接口人。

这带来两个直接后果：

第一，**进度失控的成本极高**。客户按里程碑付款，你的公司按续约活着，而项目延期最常见的原因不是技术难题，而是没人提前发现"数据权限申请了三个星期还没批下来"这种事。

第二，**线上事故没有第二道防线**。你在客户内网部署的管道挂了，没人值班帮你顶，客户的业务用户第二天上班发现报表没更新，信任就开始流失。FDE 项目里口碑崩掉往往不是因为功能没做出来，而是因为做出来的东西"不稳定"、"出了事找不到人"。

所以这一支柱的核心不是学 PMP 那套理论，而是三件事：**用最小的管理开销让项目不失控、让系统可运维、让安全合规不踩线**。下面逐节展开。

## 一、个人项目管理

### 1.1 是什么、为什么

FDE 的项目管理有一个约束前提：你只有一个人（或者两三个人），管理本身不能占用超过 10% 的时间，否则就变成"为了管理而管理"。所以目标不是流程完备，而是回答三个问题：这周交付什么？有什么会挡路？谁需要知道进展？

### 1.2 怎么做

**（1）把项目拆成以周为单位的里程碑**

一个典型的三个月 PoC（概念验证）项目，建议直接拆成 12 个周里程碑，每个里程碑必须有"客户可见的产出"。反面教材是把里程碑定义成"完成数据接入模块开发"——这是内部视角，客户看不见，也无法验收。

一个可用的拆解示例（某制造企业设备数据看板项目）：

| 周 | 里程碑（客户可见产出） | 关键依赖 |
|---|---|---|
| W1 | 现场调研完成，输出一页纸问题定义与数据资产清单 | 客户安排访谈 |
| W2 | 拿到第一批数据源只读权限，跑通样本数据抽取 | IT 部门审批账号 |
| W3 | 脏数据清洗规则 v1，数据质量报告给客户确认 | 业务方确认口径 |
| W4 | 三张核心表建模完成，样例查询可演示 | — |
| W5-W6 | 看板原型（Streamlit 或低代码）上线内测 | 客户选 5 个试用用户 |
| W7-W8 | 根据反馈迭代，指标口径全部书面确认 | 业务方签字 |
| W9 | 正式版 UI + 权限配置完成 | AD/LDAP 对接 |
| W10 | UAT 验收测试，问题清单清零 | 客户安排测试 |
| W11 | 上线、培训、操作手册交付 | — |
| W12 | 运维移交、续约/扩容方案讨论 | 双方管理层 |

注意两个要点：一是 W2 这种"拿权限"的事也被列为里程碑，因为它是典型的关键路径瓶颈（下面风险管理会讲）；二是每个里程碑都有明确的"客户确认动作"，避免到项目末尾才发现双方对"完成"的理解不一致。

**（2）每天五分钟的任务看板**

不需要 Jira。一个 Markdown 文件、一个 Notion 看板，甚至一本纸质笔记本都够。关键是固定三个区：`本周必须交付` / `进行中` / `被阻塞（写明等谁、等什么、什么时候去催）`。每天开工前扫一眼"被阻塞"区——FDE 项目延期的原因，八成躺在这一栏里。

**（3）风险登记表：提前写下会杀死项目的十件事**

项目启动第一周，花一小时把可能出问题的事写下来，每周回顾一次。FDE 项目的高频风险几乎是固定的：

- **数据权限拿不到**（概率最高）：客户 IT 审批慢、安全部门有顾虑、源系统负责人不配合。对策：第一周就发起申请，同时用客户提供的导出文件/脱敏样本先开发，不等权限到位。
- **关键干系人变动**：对接的业务负责人调岗或离职，项目失去内部赞助人。对策：永远不要只依赖一个联系人，至少维持"业务方 + IT 方"两条线。
- **需求蔓延**：客户不断加需求，范围失控。对策：所有新需求进 backlog，明确告诉客户"可以做，排进下一个阶段，本期范围不变"。
- **数据质量比预想差**：说好的主数据表，一半字段是空的。对策：拿到数据第一周就跑一遍 profiling（见下文 SQL 示例），用数字跟客户对齐预期。
- **客户内部流程**：上线要过变更委员会，每月只开一次会。对策：尽早问清楚客户的上线审批流程，倒推排期。

数据 profiling 不用买工具，SQL 就够：

```sql
-- 快速摸底一张表的数据质量：空值率、重复率、取值分布
SELECT
  COUNT(*) AS total_rows,
  COUNT(device_id) AS non_null_device_id,
  COUNT(*) - COUNT(DISTINCT device_id) AS dup_device_id,
  ROUND(100.0 * (COUNT(*) - COUNT(factory_code)) / COUNT(*), 1) AS factory_null_pct,
  MIN(event_time) AS earliest, MAX(event_time) AS latest
FROM raw_device_events;
```

把这个结果做成一页"数据质量报告"发给客户，比开三次会扯皮有效得多——它同时是需求澄清工具和风险管理工具。

**（4）向上同步：结构化、主动、坏消息早报**

驻场 FDE 要同时向两边汇报：客户方管理层和你自己公司。周报是最低成本的同步工具，模板固定四段即可：

```text
【本周进展】完成了什么（对里程碑）
【下周计划】要交付什么
【风险与阻塞】需要谁协调什么（这一条最重要）
【需要的支持】明确到人和时间
```

三条纪律：

- **坏消息早报**。发现里程碑要延，第一时间说，并带着补救方案说（"W5 原型会延两天，原因是数据权限未到，我先用样本数据顶上，权限到位后一天内切换"）。领导可以容忍延期，不能容忍惊喜。
- **报喜要有证据**。说"进展良好"不如贴一张 Demo 截图、一条"本周管道成功运行 7/7 天"的记录。
- **客户方的同步用对方的语言**。给客户领导汇报，一页纸、三个数、一个结论，不要讲技术细节。

### 1.3 常见坑

- **过度工程化管理**：一个人维护 200 行的甘特图，本身就是项目风险。管理开销超过 10% 就是浪费。
- **里程碑没有验收标准**："完成数据接入"无法验收，"客户业务方确认了 10 张表的字段口径并邮件回复确认"可以。
- **只埋头干活不同步**：现场 FDE 的可见性就是价值的一部分。客户续约谈的是"感知到的价值"，不是你实际干的活。
- **把客户的"好的"当成承诺**：涉及权限、排期、验收的关键事项，必须有书面记录（邮件、纪要），口头答应在追责时等于零。

## 二、上线与运维

### 2.1 是什么、为什么

FDE 项目的特殊性在于：客户现场通常是隔离内网，没有云厂商的托管服务，没有 7×24 的 SRE 团队，出事第一个电话打给你。而且客户的业务系统一旦依赖了你的交付物，"系统半夜挂了"就直接转化为对你个人和你公司的信任损失。上线与运维能力的目标很朴素：**让系统在你不盯着的时候也能跑，挂了能自动拉起来，真出大事能五分钟回滚**。

### 2.2 怎么做

**（1）上线检查清单（Go-Live Checklist）**

每次上线前过一遍，打印出来贴墙上都行：

```text
部署前
[ ] 配置项全部外部化（环境变量/配置文件），代码里没有硬编码的密码和 IP
[ ] 数据库变更脚本可重复执行（幂等），并已在测试环境跑过
[ ] 回滚方案已验证（不是"写了"，是真的演练过）
[ ] 客户 IT 已确认变更窗口和通知范围

部署中
[ ] 先备份：数据库 pg_dump / 配置文件打包，并验证备份文件非空
[ ] 按顺序部署：先数据层，再服务层，再前端
[ ] 部署后立即跑冒烟测试（核心接口、核心查询各验一条）

部署后
[ ] 观察日志 30 分钟，确认无异常报错
[ ] 确认定时任务/调度已正常触发
[ ] 通知干系人"已上线，如何验证，有问题找谁"
[ ] 更新部署文档（版本号、变更内容、操作人、时间）
```

备份示例（PostgreSQL，放到 cron 里每天跑）：

```bash
#!/bin/bash
BACKUP_DIR=/data/backup
mkdir -p "$BACKUP_DIR"
FILE="$BACKUP_DIR/appdb_$(date +%Y%m%d_%H%M%S).sql.gz"
pg_dump -h 127.0.0.1 -U appuser appdb | gzip > "$FILE"
# 保留最近 14 天
find "$BACKUP_DIR" -name "appdb_*.sql.gz" -mtime +14 -delete
# 备份文件为空则告警（最常见的坑：备份脚本跑了很多年，文件一直是 0 字节）
[ -s "$FILE" ] || echo "BACKUP EMPTY: $FILE" | mail -s "BACKUP FAILED" ops@example.com
```

**（2）灰度与回滚：客户环境下的务实做法**

客户内网没有 K8s 蓝绿部署那套基础设施，用最朴素的方式达到同样效果：

- **数据管道类**：新旧逻辑并行跑一个周期，新旧结果对比一致后再切流量。切流方式可以简单到一个配置开关 `PIPELINE_VERSION=v2`。
- **Web 应用类**：Docker 部署的话，新版本先起一个新端口（如 `8081`），nginx 临时把内部测试用户导过去，验证没问题再切主流量，旧容器保留 24 小时不删——这就是你的回滚预案，回滚动作就是 `docker stop new && docker start old`，三十秒完成。
- **数据库变更**：所有 schema 变更写成可回滚的迁移脚本（up/down），不要用 "直接在生产库里 ALTER TABLE 然后祈祷"。

关键原则：**回滚方案必须演练过**。没演练过的回滚预案等于没有预案——真出事时你会发现备份文件恢复不了、旧镜像已经被清掉了。

**（3）监控与告警：单人运维的最小集**

没有 SRE 团队，就自己搭一个够用的：

- **服务存活**：Uptime Kuma（自托管、Docker 一键起）盯着你的 Web 服务和 API，挂了发邮件/Webhook。
- **管道健康**：Airflow 自带失败重试和邮件告警，务必配置；再加一条"静默失败"检查——管道没报错但产出数据为 0 行，比报错更危险。在管道末尾加一条断言：

```sql
-- 数据量为零或环比暴跌时主动报错，让调度系统告警
SELECT CASE WHEN COUNT(*) = 0
  THEN CAST('FATAL: daily partition is empty' AS INT)
  ELSE 1 END
FROM dwd_device_events
WHERE dt = CURRENT_DATE - 1;
```

- **日志**：至少做到应用日志落盘 + logrotate 轮转（不然三个月后磁盘被日志撑爆，这是客户现场最常见的事故之一），关键错误日志单独一份方便检索。
- **资源监控**：`node_exporter` + Prometheus + Grafana 是标准答案，但如果客户环境不让装，一个定时跑 `df -h` 和 `free -m` 、超阈值发邮件的 shell 脚本也比没有强。

**（4）客户培训与知识转移**

FDE 项目的终极目标是"你走了系统还能活"。交付物必须包含三样：

- **操作手册**：面向最终用户，截图+步骤，写"点哪里"，不写架构。每一节以用户要完成的任务开头（"如何导出上月报表"），而不是以功能模块开头。
- **运维手册**：面向客户 IT，包括架构图一张、服务清单（端口、依赖、部署位置）、常见故障处理（"报表没更新先看 Airflow 这个 DAG"）、备份恢复步骤。写完让客户 IT 的人照着手册真的操作一遍——他们操作不下去的地方就是手册要改的地方。
- **培训**：现场培训一场 + 录屏存档。现场培训给关键用户讲，录屏留给以后入职的人看。录屏不需要剪辑，OBS 或系统自带录屏就行，朴素但管用。

**（5）交付后支持机制**

和客户明确约定支持边界，写进验收文档：响应渠道（邮件群/IM 群）、响应时间（工作日内 4 小时响应）、问题分级（系统不可用 / 功能异常 / 使用咨询分别怎么处理）、支持期多久、超期后怎么续。模糊的"有问题随时找我"会在三个月后变成你的噩梦，也对客户不负责任——他们需要的是一个可依赖的机制，不是你个人的承诺。

### 2.3 常见坑

- **"在我机器上是好的"**：所有部署用 Docker 或至少用锁定依赖的 requirements.txt / lock 文件，环境差异是现场交付的第一大时间杀手。
- **备份从未验证恢复**：每季度做一次恢复演练，把备份真的还原到一台测试机上。
- **日志撑爆磁盘**：交付三个月后最常见的宕机原因，logrotate 必须配置。
- **你一走系统就死**：所有密码、证书、部署文档集中存放在客户指定的密码管理工具或加密文档里，交接清单逐项签字。这不仅专业，也是对你自己的保护。
- **上线时间没选对**：永远不要在周五下午或节假日前一天上线，除非你想在假期里接电话。

## 三、安全与合规

### 3.1 是什么、为什么

在客户现场，数据安全是高压线：一次数据泄露事件足以终结整个项目甚至两家公司的合作关系，而且责任往往落到具体操作的人头上。FDE 天天泡在客户的真实数据里，是最容易出事的位置。合规则决定了你能不能拿到数据、系统能不能上线——等保测评、安全评审不过，前面所有交付都是零。

好消息是，FDE 不需要成为安全专家，需要的是**建立正确的本能反应**：什么数据能碰、怎么碰、碰完留下什么痕迹。

### 3.2 怎么做

**（1）第一原则：不确定能不能碰的数据，先不碰**

看到一张表里疑似有身份证号、手机号、病历，而你的任务说明里没有明确授权使用这些字段——先不查、不导、不复制，去问数据 Owner 拿到书面授权再说。这一条看起来慢，实际上是最快的路径：出了事再解释，代价是数量级的差距。

**（2）最小权限与访问控制**

- 向客户申请数据权限时，**按需申请**：只读账号、只给需要的库表、限定有效期。一上来要 DBA 权限，安全部门必然警惕，反而拖慢审批。
- 你自己的系统里，按角色做访问控制（RBAC），客户几乎必问"谁能看什么"。数据库层用视图控制敏感字段：

```sql
-- 给业务用户建脱敏视图，而不是直接授权原始表
CREATE VIEW v_customer_safe AS
SELECT
  customer_id,
  LEFT(phone, 3) || '****' || RIGHT(phone, 4) AS phone_masked,
  region,
  total_amount
FROM customers;

GRANT SELECT ON v_customer_safe TO biz_readonly;
-- 原始表不授权给业务账号
```

- 应用层密钥绝不进代码库：用环境变量或客户指定的密钥管理方案。`git log` 里出现过一次生产密码，就按泄露处理——改密码、清历史、通报。

**（3）脱敏：开发测试不用生产明文**

需要把生产数据拉到测试环境调试时，先脱敏再落地。常用字段的处理方式：

- 手机号/身份证：保留前 3 后 4，中间打码（如上 SQL）。
- 姓名：替换为随机生成的假名（Python 里 `Faker` 库一行搞定）。
- 金额等敏感数值：加一个固定比例的随机扰动，或整体做区间化。
- 银行卡、病历这类强敏感数据：能不拿就不拿，开发阶段用构造的假数据。

一个经常被忽视的点：**日志里也会泄露数据**。打印 SQL 报错、异常堆栈时不要把整行数据打进日志，特别是包含个人信息的对象。

**（4）审计日志：证明你做了什么**

客户安全部门事后审计时，审计日志是你最好的保护。最低要求：谁在什么时间访问了什么数据、做了什么导出操作，有据可查。应用里记录关键操作的审计表（操作人、时间、动作、对象、结果），数据库层开启客户要求的审计插件（如 PostgreSQL 的 pgaudit）。给客户传文件、发数据，一律走客户认可的渠道并保留记录，不用个人邮箱、个人网盘、个人微信传任何含客户数据的文件——这条没有例外。

**（5）合规要求的基本认知**

不需要背法规条文，但要知道自己项目落在哪个框架里：

- **等保（网络安全等级保护）**：国内政企客户必问。你的系统可能被纳入客户某个等保级别（常见二级/三级）的测评范围，会影响密码策略、日志留存、访问控制的设计。项目早期就问客户："这套系统要不要过等保测评？按几级？"答案会直接影响架构。
- **GDPR / 个人信息保护法（PIPL）**：涉及个人信息（特别是跨境场景）时，关注最小必要原则、用户授权、数据删除权。外企客户会有自己的数据出境评估流程。
- **行业合规**：金融（人行/银保监的要求）、医疗（健康医疗数据的安全管理办法）、政务（数据不出政务网）各有红线，进场第一周就向客户 IT 安全接口人要一份书面的安全要求清单。

**（6）与客户安全部门打交道**

安全部门不是你的敌人，是帮你背书的人。三个实用做法：第一，项目早期主动约安全接口人，把你的数据流图给他看，让他 early review——比他上线前一周再来拦你强一百倍；第二，他提的要求逐条书面回复"如何满足"，形成一份安全响应文档，这份文档本身就是交付物；第三，拿不准的操作（比如要临时开个端口、要导出一份数据），先问再做，问的动作本身就在积累信任。

### 3.3 常见坑

- **把生产数据留在自己笔记本上**：项目结束或离场时，按客户要求清理本地数据并留证。驻场电脑上的数据不属于你。
- **为了方便绕过 VPN/堡垒机**：被发现一次，信任清零，没有第二次机会。
- **用个人网盘/邮箱传数据**：哪怕只是为了"快点发给客户看一下"，也是事故。
- **忽视依赖组件的漏洞**：客户的安全扫描会扫你的 Docker 镜像和依赖库（常用工具如 Trivy），上线前自己先扫一遍修掉高危，别等扫描报告发到你领导那里。
- **把"客户没提"当"没有要求"**：主动问安全要求是你的责任，出事后"客户当时没说"不构成免责理由。

## 学习路径建议

这一支柱没法靠看书学会，但可以有意识地练：

- **第 1-2 周（打底）**：给自己做一个真实的小项目（哪怕是个人数据管道），强制走完整流程：写周里程碑、配 cron 备份、加监控告警、写一页运维手册。流程跑过一遍，比读十篇项目管理文章有用。
- **第 1-3 个月（跟项目）**：在现有项目里主动承担三件"没人爱干的活"：写周报、维护上线 checklist、整理运维文档。这三件事是这一支柱的肌肉训练。
- **第 3-6 个月（补框架）**：读一遍《凤凰项目》（The Phoenix Project）理解运维与交付的关系；把风险登记表、周报、上线 checklist 三份模板沉淀成自己的模板库，之后每个项目直接复用。
- **持续**：每次项目出问题（延期、故障、返工），写一份不超过一页的复盘，只回答两个问题：最早的信号是什么？下次在第几周能发现？一年后这份复盘集就是你最值钱的资产。

## 自测清单

以下每条都能答"是"，说明这一支柱基本过关：

- [ ] 能把一个三个月项目拆成 12 个客户可见的周里程碑，每个里程碑有明确验收标准
- [ ] 手上有自己的周报模板、风险登记表模板、上线 checklist 模板，并且在真实项目里用过
- [ ] 能在客户内网无云环境下完成：Docker 部署、定时备份（并验证恢复）、服务监控告警
- [ ] 说得出自己系统的回滚步骤，并且真的演练过一次
- [ ] 交付物包含用户手册、运维手册、培训录屏三件套，客户团队能不看你自己操作
- [ ] 知道本项目的数据里哪些字段是敏感的，脱敏规则是什么，权限审批走到哪一步
- [ ] 能用一句话说清本项目的合规框架（等保几级 / 是否涉及个人信息 / 行业特殊要求）
- [ ] 出现问题时，第一反应是"先恢复、再定位、后追责"，并且知道怎么向两边管理层同步坏消息

## 小结

这一支柱的本质一句话：**现场只有你一个人时，用最少的流程保证项目不失控、系统不出事、安全不踩线——管理是为交付服务的，不是反过来。**
