# FDE 产品思维深挖：从项目到产品的抽象，怎么抽、抽多深、什么时候不抽

> 系列三级专题 · 对应《FDE 技能栈之产品思维》第一节「从项目到产品的抽象」。父级文章讲了"三个客户"提问法、配置与 if-else 之分、三次原则，这篇往下再走一层：抽象的具体操作方法、一次完整的重构示范、接口边界怎么划、以及什么时候明确不该抽象。

## 开篇：第三次写同一个东西的那个下午

我在第二个客户现场遇到过一个具体的时刻。客户是家物流企业，要把承运商系统的运单数据接进我们平台。我打开编辑器准备写映射逻辑，越写越觉得眼熟——字段清洗、编码转换、单位归一、状态枚举对齐，这套东西我在上一家制造业客户那里写过一遍，再上上家做设备数据接入时又写过一遍。

三份代码摆在面前，逻辑 80% 相同，但谁也复用不了谁：第一份把客户字段名硬编码在 Python 字典里，第二份把映射规则写死在 SQL CASE WHEN 里，第三份（我正在写的）如果再图快，就是第四份孤本。更要命的是，第一份代码里修过的一个时区 bug，第二份里还存在——因为没人知道它们是"同一个东西"。

那天下午我把手头的定制活停下来，花了两天把三份代码重构成一个配置驱动的映射模块。之后第三个、第四个客户的接入，从"写一周代码"变成"写半天配置加半天验证"。

这篇文章讲的就是那个下午我具体做了什么：**怎么找到该抽象的东西、怎么动手抽、抽到什么程度停手、抽完之后怎么让它真的被下一个人用上**。前提是你已经读过父级文章——"三个客户"提问法、三次原则这些基本概念这里不再重复，我们直接进操作层。

## 一、抽象第一步：变化点分析，而不是设计模式

很多工程师一提抽象就去想架构、想设计模式，方向就错了。FDE 现场的抽象只有一个出发点：**把"每次都不一样"的部分和"从来都不变"的部分分开**。这个分析有名字，叫变化点分析（variation point analysis），做法朴素到就是填一张表。

拿数据接入这个场景，把三个客户的实现摆在一起，逐行对比，把差异点全部列出来：

| 维度 | 客户 A（制造） | 客户 B（物流） | 客户 C（能源） | 是"变"还是"不变" |
|------|------|------|------|------|
| 数据源类型 | Oracle | MySQL | REST API | 变 |
| 源字段名 | `EQP_NO`, `VAL` | `carrier_id`, `weight` | `point_code`, `reading` | 变 |
| 目标模型 | 统一成 `entity_id` + `value` + `ts` | 同左 | 同左 | **不变** |
| 单位换算 | 摄氏度→开氏度 | 磅→千克 | 无 | 变（可选步骤） |
| 状态码枚举 | 0/1/2 → 停机/运行/故障 | A/D/P → 到达/发出/在途 | 无状态 | 变 |
| 清洗顺序 | 先类型转换再映射 | 同左 | 同左 | **不变** |
| 失败处理 | 脏数据进隔离表，任务继续 | 同左 | 同左 | **不变** |

填完这张表，抽象的边界自己就浮出来了：**处理流程（抽取 → 类型转换 → 字段映射 → 枚举翻译 → 单位换算 → 写入 → 失败隔离）是不变的核心；每一步的具体参数是变的配置**。

这一步的两个要点：

- **至少要有两个真实样本才填得出这张表。** 只有一个客户时，你看哪一行都像是"会变"的，抽象出来全是配置项，等于没抽。这就是父级文章"三次原则"在操作层的原因——不是迷信数字三，是一个样本根本做不出变化点分析。
- **"不变"的那几行才是模块的本体。** 很多人抽象了半天，把变的部分抽成配置了，核心流程却散落在各客户的代码里没收敛——那只是把乱的地方搬了家。抽象的目标是**核心逻辑只有一份**，配置可以有 N 份。

## 二、实操：一次完整的重构 walkthrough

下面是那次重构的浓缩版，从"反模式"到"可复用模块"的完整路径。

### 2.1 起点：典型的现场定制代码

```python
# ingest_logistics.py —— 客户 B 的接入脚本，典型的"能用就行"
def ingest(rows):
    results = []
    for r in rows:
        entity_id = r["carrier_id"]            # 字段名写死
        value = float(r["weight"]) * 0.4536    # 磅转千克，公式写死
        status_map = {"A": "arrived", "D": "departed", "P": "in_transit"}
        status = status_map.get(r["st"], "unknown")  # 枚举写死
        ts = datetime.strptime(r["ship_time"], "%m/%d/%Y %H:%M")  # 格式写死
        results.append({
            "entity_id": entity_id, "value": value,
            "status": status, "ts": ts,
        })
    write_to_platform(results)
```

这段代码交付本身没问题——它两天写完，跑得很稳。问题在于它的每一个决策都焊死在代码里，下一个客户来了只能复制粘贴再改，改出第四份孤本。

### 2.2 第一步重构：把决策搬进配置

按照变化点分析表，把所有"变"的行抽成 YAML：

```yaml
# mappings/customer_b_waybill.yaml
source:
  type: mysql
  table: shipment
mapping:
  entity_id: carrier_id        # 目标字段 ← 源字段
  value: weight
  status: st
  ts:
    field: ship_time
    format: "%m/%d/%Y %H:%M"
transforms:
  value:
    - op: multiply
      factor: 0.4536           # 磅 → 千克
enums:
  status:
    A: arrived
    D: departed
    P: in_transit
on_error: quarantine           # 脏数据进隔离表
```

### 2.3 第二步：核心引擎只写一次

引擎代码里不出现任何客户名、字段名、魔法数字：

```python
# ingest_engine.py —— 唯一的一份核心逻辑
def ingest(rows, config: dict) -> IngestResult:
    results, quarantined = [], []
    for row in rows:
        try:
            record = apply_mapping(row, config["mapping"])
            record = apply_transforms(record, config.get("transforms", {}))
            record = apply_enums(record, config.get("enums", {}))
            results.append(record)
        except (KeyError, ValueError) as e:
            quarantined.append(QuarantineRow(raw=row, reason=str(e)))
    write_to_platform(results)
    if quarantined:
        write_to_quarantine(quarantined)
    return IngestResult(ok=len(results), quarantined=len(quarantined))
```

注意一个细节：`on_error: quarantine` 这个失败隔离策略，是变化点分析表里"不变"的那行——所以它不应该出现在配置里让客户选，而应该作为引擎的默认行为焊死在核心代码里。**配置项只留给真正会变的东西**，每多一个配置项都是未来用户的一个理解负担。

### 2.4 第三步：给配置加校验，别信手写的 YAML

配置驱动的模块有一个新的失败模式：配置写错了，跑到半夜才炸。所以配置必须有 schema 校验，加载时就报错，报错信息要指得出是哪一行哪个字段。用 pydantic 几十行就够：

```python
# config_schema.py
from pydantic import BaseModel, field_validator

class TsMapping(BaseModel):
    field: str
    format: str

    @field_validator("format")
    @classmethod
    def check_strftime(cls, v: str) -> str:
        try:
            datetime.now().strftime(v)
        except ValueError:
            raise ValueError(f"非法时间格式: {v}")
        return v

class IngestConfig(BaseModel):
    source: dict
    mapping: dict
    transforms: dict[str, list[dict]] = {}
    enums: dict[str, dict[str, str]] = {}
    on_error: str = "quarantine"

def load_config(path: str) -> IngestConfig:
    with open(path) as f:
        return IngestConfig(**yaml.safe_load(f))   # 配置不合法在这里就炸
```

再加一条铁律：**每份配置配一个冒烟测试**。不用写正式单测，一个脚本就够——拿客户提供的 10 行样本数据跑一遍引擎，断言输出条数和关键字段非空：

```bash
python -m ingest_engine.smoke_test \
    --config mappings/customer_b_waybill.yaml \
    --sample samples/customer_b_head10.csv
```

新客户接入的验收标准从"代码跑通了"变成"配置 + 冒烟测试通过"。这个标准客户方的 IT 也能看懂、能自己执行，交付的信任成本直线下降。

### 2.5 重构完的目录形态

```
ingest-engine/
├── ingest_engine/        # 核心逻辑，全公司只有这一份
│   ├── engine.py
│   ├── config_schema.py
│   └── transforms.py
├── mappings/             # 每个客户一个目录
│   ├── customer_a_equipment.yaml
│   └── customer_b_waybill.yaml
├── samples/              # 每个配置配一份样本数据
└── README.md             # 怎么写一份新配置，30 分钟能上手
```

判断这次抽象成功与否的标准很硬：**客户 C 接入时，工程师只动了 `mappings/` 和 `samples/` 两个目录，核心代码一行没改**。只要改了一行核心代码才能满足新客户，说明抽象边界划错了，回去改边界，不要在核心代码里加 `if customer == "C"`。

## 三、抽象的边界与接口设计：三件事必须定死

模块抽出来了，下一个问题是边界。FDE 的通用模块会被其他驻场工程师在高压环境下使用，接口不清楚的模块比没有模块更糟糕。三件事必须定死：

**1. 明确公开契约，其余都是私有。** 对上面的引擎来说，公开契约就三样：配置文件的 YAML schema、输入数据的格式约定、输出和隔离表的 schema。引擎内部 `apply_transforms` 怎么实现，使用者不需要知道，也不许依赖。写进 README 第一段：**"你只被允许依赖以下三样东西"**。没有这句话的模块，使用者会自然地开始依赖你的内部细节，然后你每次改实现都会炸掉某个客户现场。

**2. 配置 schema 要版本化。** 配置格式一定会演进（比如后来要支持多表 JOIN 的源），在配置里加一行显式版本号：

```yaml
version: "1"
source:
  type: mysql
```

引擎加载时检查版本，遇到不认识的版本号直接拒绝并提示，而不是默默按新格式解析然后行为诡异。等真的有 breaking change 时，老配置配老版本号继续跑，新格式用 `version: "2"`，这就是给驻场同事留的活路——他们可能在隔离网里，升级一次引擎要走两周审批。

**3. 默认值要替用户做决定。** 每加一个配置项，先问"能不能用合理默认值消掉它"。上面例子里 `on_error` 默认值是 `quarantine`，99% 的客户不该改它。一个需要填 30 个字段的配置文件，和一个只需填 6 个、其余有安全默认值的配置文件， Adoption 率差一个数量级。**抽象的易用性决定它会不会真的被复用**——难用的通用模块的命运是被复制粘贴绕过，然后再次腐化成孤本。

## 四、什么时候明确不该抽象

抽象不是美德，是投资。投资就要算账。算式很简单：

```
抽象成本 = 额外开发时间 + 后续维护一个通用模块的成本 + 抽象错方向的重做风险
复用收益 = 单次接入节省的时间 × 预期复用次数
```

下面四种情况，账算不平，**不要抽**：

- **只有一个样本，且看不到第二个客户在哪。** 父级文章的三次原则在此。一个样本时你做的"通用设计"必然过拟合这个样本的特例，第二个客户来了接口要推翻，白做两遍。
- **变的是流程本身，不是参数。** 变化点分析里如果"处理流程"那一行都是"变"——A 客户要先清洗再映射，B 客户要先映射再聚合，C 客户流程完全不同——那你要抽的不是配置，是 Pipeline 框架，成本高一个量级，大概率超出了你驻场项目的合理范围。这种信号应该写进现场洞察反馈给产品团队，而不是自己硬上。
- **需求本身可能是应激产物。** 上周领导提了一嘴、此后再没人提的需求，先按最定制的方式交付甚至先不交付（父级文章的"两周过滤器"），更不值得为它建通用能力。
- **你下周就要撤场，且没人接盘。** 通用模块需要 owner。抽出来没人维护的模块，半年后就是仓库里一坨没人敢动的代码，还不如留下一份注释良好的定制实现。

反过来，有一个信号要**立刻**抽：你发现自己在复制粘贴自己三个月前写的代码。复制粘贴是身体比大脑先识别出了模式。

## 五、抽象完只做了一半：让模块活着的三件事

很多 FDE 的抽象死在这一步：模块写好了，埋在自己的项目仓库里，离职或撤场后无人知晓。抽象的产出物不是代码，是"**别人能捡起来用**"这个状态。具体三件事：

**1. 交接包 checklist。** 模块进入共享仓库时，必须凑齐：

- [ ] README：30 分钟上手指南，包含一个完整的"从零配一个新客户"的 walkthrough
- [ ] 至少两份真实客户的配置作为参考样例
- [ ] 冒烟测试脚本和样本数据
- [ ] 已知边界：明确写"本模块不支持什么"（比如"不支持流式源，只支持批处理"）
- [ ] 一个指定的 owner（通常是你，直到交接给产品团队）

最后一项"已知边界"最容易被忽略，价值却最高——下一个 FDE 在现场被客户追问"你们这个能不能接 Kafka"时，README 里一句"不支持，见洞察 #23 的评估"能省他三天的评估时间，也避免他给客户错误承诺。

**2. 反哺产品团队时带上证据，不只是结论。** 父级文章讲了现场洞察的格式，这里补一个关键差别：推动产品化的洞察和普通的现场反馈不一样，必须带**复用次数的证据**。"三个客户各自实现了同一个模式"和"我觉得这个会有用"是完全不同的两种输入。前者附上三个配置的链接和变化点分析表，产品团队可以直接立项；后者只会进 backlog 吃灰。

**3. 度量复用，让抽象的价值可见。** 给自己记一笔简单的账：

| 模块 | 抽象投入 | 复用次数 | 单次接入成本变化 | 累计节省 |
|------|------|------|------|------|
| ingest-engine | 2 人日 | 4 个客户 | 5 人日 → 1 人日 | 14 人日 |

这张表同时是你的价值量化素材（父级文章第二节的 Value Log 里应该有它一行）和续约谈判的弹药——"我们的接入框架让贵司二期上线周期缩短了 60%"比"我们技术架构先进"有力得多。

## 六、常见坑

父级文章已经列了四个坑（单样本抽象、牺牲交付速度、抽完不传播、配置地狱），这里补四个操作层的：

- **把"不变"的东西也做成配置。** 处理顺序、失败策略这些核心行为进了配置，客户现场有人手贱改了，行为全变还查不出来。配置项的唯一合法性来源是变化点分析表里"变"的那几行。
- **配置和代码用两套发布节奏。** 客户 A 的配置升级依赖引擎的新 transform，但现场引擎版本没升，半夜管道炸了。对策：配置里声明 `min_engine_version`，引擎加载时校验，不匹配就拒绝启动。
- **核心代码里残留"最后一个客户"的痕迹。** 重构时把当前客户的字段名设成了默认值，三个月后所有人都以为那是标准。默认值必须是真正的领域通用值，或者干脆没有默认值、强制必填。
- **抽象边界泄露给终端用户。** 客户业务人员不应该感知到"配置"的存在——他们看到的是一个功能。如果业务人员需要理解 YAML 才能用起来，说明抽象层放错了位置，配置应该是驻场工程师的工具，不是客户的负担。

## 七、练习方法与自测

**练习一：变化点分析（成本一小时）。** 翻出你过去做过的两个项目（不一定是客户项目，自己的两个爬虫、两个脚本都行），找其中重复出现的逻辑，填一张变化点分析表。重点观察：你事先以为"会变"的有多少其实不变？这个练习做三次，你对抽象边界的直觉会明显变准。

**练习二：配置化重构（成本一个周末）。** 挑一段硬编码最严重的旧代码，按本文第二节的五步走：填表 → 抽配置 → 收敛核心 → pydantic 校验 → 冒烟测试。验收标准：用一个虚构的"新客户"需求检验——只写一份新 YAML 能不能跑通？需要改核心代码就说明边界没划对。

**练习三：写"已知边界"（成本二十分钟）。** 给你手头任何一个模块写一节"不支持什么"。这个练习练的是接口意识——说不清楚不支持什么的人，通常也没想清楚支持什么。

**自测标准：**

- [ ] 我能为手头任何一段定制代码填出变化点分析表，并指出哪些行是"不变"的核心
- [ ] 我的通用模块里，新客户接入不需要改动核心代码，有冒烟测试为证
- [ ] 每个配置项都能回答"为什么它需要存在，默认值为什么不能覆盖它"
- [ ] 模块 README 里有明确的公开契约、版本策略和"不支持什么"
- [ ] 我给产品团队的洞察里带着复用次数的证据，不是裸结论
- [ ] 我有一张复用账本，说得出每个抽象投入了多少、收回了多少
- [ ] 我同样说得出哪些东西我**决定不抽象**，以及理由

---

## 结语

抽象能力的本质不是编程技巧，是一种记账习惯：每次写定制代码时多问一句"这是第几次写这个东西"，每次想抽通用模块时多问一句"这笔投资收得回来吗"。前者让你不错过模式，后者让你不制造过度工程。两问都答得上来，"从项目到产品"就不是口号，是你仓库里那个被四个客户复用的 `mappings/` 目录。
