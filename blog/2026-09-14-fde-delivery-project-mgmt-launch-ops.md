# FDE 上线与运维实战：一个人把系统送上生产，并让它活得比你久

> 系列深度专题 · 本文是 [FDE 技能栈（五）：交付与项目管理](./2026-09-14-fde-delivery-project-mgmt.md) 中「上线与运维」一节的展开。父级文章讲了上线 checklist、灰度回滚原则和监控最小集，本文解决的是更细一层的问题：上线当天每个小时干什么、新旧系统怎么对账、数据库变更怎么回滚、半夜出事怎么处理。

## 一个现场场景

周五下午四点，某制造企业客户内网。你开发的设备数据看板按计划下周二上线，业务方负责人临时走进来："集团领导周一上午来视察，能不能周日晚上把系统切上去？"客户 IT 说变更窗口可以特批，但"出了事你自己负责回滚"。你看了眼手表——距离你回家的高铁还有三小时。

这个场景里塞满了 FDE 上线运维的典型约束：时间被客户业务节奏绑架、决策压力集中在你一个人身上、没有 SRE 兜底、内网环境连 Docker Hub 都连不上。父级文章给的 checklist 能告诉你"要做什么"，但挡不住这个场景里真正会杀死你的问题：上线步骤只存在于你脑子里、新旧数据没对过账、回滚方案从没演练过。

所以本文只讲一件事：**把上线从"一次提心吊胆的手工操作"变成"一份任何人照着做都能执行完的文件"**。

## 一、上线方案：写一份分钟级的 Runbook

### 是什么、为什么

Checklist 回答"做没做"，Runbook 回答"第几分钟做什么、命令是什么、预期看到什么、失败了退回哪一步"。区别很关键：上线当晚你处于高压状态，认知能力下降，任何需要"想一想"的环节都是事故温床。Runbook 的本质是**把决策从上线当晚提前到你头脑清醒的当天下午**。

另一个更实际的理由：客户的变更委员会、IT 部门往往要求提交书面上线方案才批窗口。Runbook 写好了，审批材料和执行手册就是同一份东西。

### 怎么做

一份能用的 Runbook 长这样（Markdown，控制在两页以内）：

```markdown
# 看板系统 v1.2 上线 Runbook
- 变更窗口：2026-09-20（周日）20:00-22:00
- 执行人：张三（FDE）  复核/见证：客户 IT 李四
- 影响范围：看板 Web 服务 + 每日数据管道；不影响源系统
- 回滚决策人：张三；回滚触发条件见文末

## 前置条件（19:30 前确认，任一不满足则取消上线）
- [ ] 备份完成且非空：/data/backup/appdb_20260920_*.sql.gz
- [ ] 旧版本容器 app-web:v1.1 确认存在（docker images | grep v1.1）
- [ ] 客户 IT 确认窗口内无其他变更

## 执行步骤
| 时间 | 步骤 | 命令/操作 | 预期结果 | 失败则 |
|---|---|---|---|---|
| 20:00 | 停管道调度 | airflow dags pause daily_etl | UI 显示 paused | 不影响，继续 |
| 20:05 | 数据库迁移 | psql -f migrations/012_add_shift.sql | 输出 ALTER TABLE | 执行回滚 R1 |
| 20:10 | 起新版本（8081 端口） | docker compose -f compose.v1.2.yml up -d | curl :8081/health 返回 ok | 执行回滚 R2 |
| 20:15 | 内部验证 | 用测试账号登录 :8081，跑 5 条核心查询 | 数据与旧版一致 | 执行回滚 R2 |
| 20:30 | 切流量 | 改 nginx upstream 指向 8081，nginx -s reload | :8080 返回新版页面 | 执行回滚 R3 |
| 20:35 | 冒烟测试 | 见附录 5 条用例 | 全部通过 | 执行回滚 R3 |
| 20:50 | 恢复调度 | airflow dags unpause daily_etl | 下次调度正常 | 人工补跑 |
| 21:00 | 观察期 | 盯日志 + 监控 30 分钟 | 无 ERROR 级日志 | 视情况回滚 |

## 回滚预案
- R1（迁移失败）：psql -f migrations/012_add_shift.down.sql
- R2（新版起不来）：docker compose -f compose.v1.2.yml down，旧容器未动，无需其他动作
- R3（切流后异常）：nginx upstream 改回 8080，nginx -s reload，预计 1 分钟
- 回滚触发条件：冒烟测试任一失败 / 观察期出现 5xx 比例 >1% / 核心查询结果与旧版不一致

## 上线后
- [ ] 通知干系人群：已上线、验证方式、问题联系人
- [ ] 旧容器保留 24 小时，次日确认无回滚需求后清理
- [ ] 更新部署文档：版本、变更内容、操作人、实际耗时
```

三个要点：

**前置条件里写"取消上线"的退出机制。** 备份没完成、旧镜像被清理了、窗口被别的变更占了——任何一个不满足，当晚就不上。提前把取消条件写下来，是帮你在客户施压"都准备好了就试试呗"的时候有依据说不。

**每一步都有"预期结果"和"失败则"。** 没有预期结果的步骤等于没验证；没有回退路径的步骤是单点赌注。如果某一步写不出"失败则"，说明你的部署架构有问题，回去改架构，不是改文档。

**回滚触发条件提前定义，且量化。** "感觉不太对就回滚"在高压下会被侥幸心理打败。写成"5xx 超过 1%""核心查询对不上"这种可判定的条件，执行时不需要纠结。

### 常见坑

- **Runbook 写完从不演练。** 上线前一周在测试环境（哪怕是自己笔记本上的虚拟机）按 Runbook 完整走一遍，包括回滚。你会发现文档里至少三处"想当然"。
- **步骤粒度过粗。** "部署新版本"不是一步，它展开是停旧、起新、验证、切流四步，每步都可能失败。
- **只写技术步骤，漏了人的动作。** 通知谁、谁在场见证、几点给客户领导发结果——这些不写，上线当晚一定漏。

## 二、灰度切换：新旧系统怎么对账

### 为什么单独讲

父级文章给了灰度的原则：新旧并行、配置开关切流。但数据管道的灰度有一个 Web 服务没有的问题：**你怎么证明新管道的产出和旧管道"一样对"？** "跑了一周没报错"不是答案——静默错误比报错危险得多。

### 怎么做：对账三件套

**（1）行数与总量对账。** 新旧管道并行跑一个完整业务周期（日报就跑 7 天），每天跑一条对账 SQL：

```sql
-- 新旧两版产出表的每日对账：行数、关键金额总和、空值数
WITH old_v AS (
  SELECT dt, COUNT(*) AS cnt, SUM(amount) AS total_amt,
         COUNT(*) - COUNT(device_id) AS null_id_cnt
  FROM dwd_device_events_v1 GROUP BY dt
),
new_v AS (
  SELECT dt, COUNT(*) AS cnt, SUM(amount) AS total_amt,
         COUNT(*) - COUNT(device_id) AS null_id_cnt
  FROM dwd_device_events_v2 GROUP BY dt
)
SELECT o.dt,
       o.cnt AS old_cnt, n.cnt AS new_cnt,
       n.cnt - o.cnt AS cnt_diff,
       ROUND(n.total_amt - o.total_amt, 2) AS amt_diff
FROM old_v o JOIN new_v n ON o.dt = n.dt
WHERE ABS(n.cnt - o.cnt) > o.cnt * 0.001       -- 行数差异超 0.1% 报警
   OR ABS(n.total_amt - o.total_amt) > 0.01;   -- 金额必须分毫不差
```

**（2）差异容忍度要分指标定，不要一刀切。** 上面例子里的规则是典型的现场约定：金额类指标必须完全相等（财务要拿去对账的），行数允许 0.1% 浮动（新旧管道对晚到数据的处理窗口可能不同）。**容忍度不是工程师自己拍的，要写成文档发给业务方确认**——"差异在这个范围内视为一致"，这句话需要对方书面认可，否则切换后任何差异都会被解读成"新系统不准"。

**（3）切换用配置开关，回切也要演练。** 切换动作越简单越好，理想状态是改一个环境变量重启服务。关键是：**切换一周后，主动回切一次再切回来**。听起来多此一举，但这是唯一低风险的回滚演练机会——此时新旧系统都在跑，回切失败代价为零。等真出事再第一次回切，你永远不知道会发生什么。

### 常见坑

- **并行期太短。** 只并行一两天，覆盖不到月末结账、周末空跑这类边界场景。至少覆盖一个完整的业务周期。
- **只对"有没有数据"，不对"数据对不对"。** 行数一致但 join 逻辑写反了的案例，每个驻场 FDE 都能讲出一个。
- **切换后立刻删旧管道。** 旧管道保留运行一个观察期（建议两周），产出存着不展示——这是你最便宜的对照组和后悔药。

## 三、数据库变更：expand-contract 模式

### 为什么

上线翻车的高危区不是应用代码——代码可以整个替换——而是数据库。`ALTER TABLE` 一旦执行，旧代码可能立刻报错，回滚就变成"把数据改回去"，而有新数据写入后根本改不回去。客户内网没有托管数据库的 PITR（时间点恢复）可用时，这个问题尤其致命。

### 怎么做

原则是**把一次破坏性变更拆成"先扩展、后收缩"两次上线**：

```text
第一次上线（expand，只加不改）：
  - 加新列 / 新表，不动旧列
  - 新代码同时写新旧两处（双写），读仍以旧列为准
  - 回填历史数据到新列（后台脚本分批跑，别锁表）

观察期（至少一个业务周期）：
  - 校验新旧列数据一致
  - 读切换：新代码改读新列，旧列仍在写（保险丝）

第二次上线（contract，下次版本再做）：
  - 停写旧列，确认无人依赖后，再考虑删除
```

以"设备表拆分工段字段"为例，迁移脚本：

```sql
-- 012_expand.sql：只加，不改
ALTER TABLE devices ADD COLUMN IF NOT EXISTS work_section VARCHAR(32);
-- 回填分批做，避免长事务锁表（生产库大忌）
UPDATE devices SET work_section = split_part(location_code, '-', 2)
WHERE id BETWEEN :batch_start AND :batch_end
  AND work_section IS NULL;
```

配套纪律：

- **迁移脚本必须幂等**（`IF NOT EXISTS`、可重复执行不报错），上线重试时不至于把库改到一半的状态。
- **大表结构变更先测耗时。** 在测试环境用同量级数据跑一遍，估算锁表时间，写进 Runbook 的预期结果里。生产上一张千万行的表 `ADD COLUMN` 带默认值，在旧版 PostgreSQL 上会重写整表锁几分钟，这几分钟业务就是停的。
- **删除类操作永远推迟到下一个版本。** 没有"这次顺便清一下"这种事。

## 四、事故响应：半夜电话来了怎么办

### 为什么

客户环境里你就是最后一道防线。凌晨两点客户值班员打来电话说"看板打不开了"，你接下来三十分钟的处置质量，决定了这个项目在客户心里的成色。处置能力不靠天赋，靠提前准备好的流程。

### 怎么做：四步 SOP

**第一步：先恢复，后定位。** 铁律。能重启恢复就先重启，能回滚就先回滚，根因分析等服务恢复之后再做。唯一例外：怀疑数据被破坏（误删、错写）时先停写、保护现场再恢复——数据损坏会随时间扩大，服务可用性反而可以等。

**第二步：留证据。** 恢复之前花两分钟抓现场，否则重启之后什么线索都没了：

```bash
# 最小现场采集，存成文件再动手恢复
mkdir -p ~/incidents/$(date +%Y%m%d_%H%M) && cd $_
docker ps -a > docker_ps.txt
docker logs --tail 500 app-web > app.log 2>&1
df -h > disk.txt; free -m > mem.txt
tail -n 200 /var/log/nginx/error.log > nginx_err.txt
```

**第三步：同步干系人。** 给客户对接人的第一条消息控制在三句话：什么事、影响什么、预计什么时候恢复（不知道就说"排查中，每 30 分钟同步一次"）。**沉默是事故处置中最扣分的行为**——客户不怕系统坏，怕的是坏了没人管、没人说。

**第四步：写事故报告。** 24 小时内发出，模板固定五段：

```markdown
## 事故报告：看板服务不可用（2026-09-21）
- 时间线：02:10 告警触发 → 02:25 响应 → 02:40 定位为磁盘写满 → 02:50 清理日志恢复
- 影响：看板不可用 40 分钟，数据无丢失，当日管道延迟 2 小时已补跑
- 根因：应用日志未配置轮转，调试日志在周末批量任务下暴涨，磁盘写满
- 直接对策（已完成）：配置 logrotate，磁盘预留 20%
- 防复发（本周内）：加磁盘使用率告警（>80% 触发）；排查其余服务日志配置
```

注意这个模板的写法：**先讲影响和恢复（客户关心的），再讲根因和对策（建立信任的）**。"防复发"必须有具体动作和期限，空泛的"后续加强监控"等于没说。

### 告警分级，避免自己把自己淹没

一个人运维，告警疲劳是真实的风险——告警太多，你两周后就开始忽略告警，等于没有告警。只分两级：

- **P1（电话/短信级，立即处理）**：服务不可用、数据错误、备份失败。这类告警必须少而准，一个健康的系统一个月不该超过三次。
- **P2（邮件级，工作时间处理）**：磁盘超 80%、管道延迟但未失败、证书 30 天内到期。

管道延迟告警用 Airflow 的 SLA 或调度后检查即可；磁盘告警最简版本就是一个 cron：

```bash
# /etc/cron.daily/disk_check —— 超阈值发邮件
#!/bin/bash
USAGE=$(df / | awk 'NR==2 {gsub(/%/,""); print $5}')
[ "$USAGE" -gt 80 ] && df -h | mail -s "ALERT: disk ${USAGE}% on $(hostname)" ops@example.com
```

## 五、运维移交：让系统活得比你久

父级文章讲了交付三件套（用户手册、运维手册、培训录屏），这里补两个执行层面的硬要求。

**移交验收用"盲操作"测试。** 运维手册写完，约客户 IT 的人做一次实战演练：你不说话、不提示，让他照着手册完成三个动作——重启服务、恢复一次备份、查一条错误日志。他卡住的地方就是手册要补的地方。这一步不做，手册的真实质量你永远不会知道，直到你离场后某个凌晨被电话叫醒。

**交接清单逐项签字，尤其是"钥匙"。** 账号密码、证书、部署文档的存放位置（客户指定的密码管理工具）、监控告警的接收人变更——列成表格，每项写清"移交内容、接收人、日期、签字"。这不是形式主义：系统三个月后出事，这份清单是区分"系统本身的问题"和"移交不清的问题"的唯一依据，保护的是你自己。

**约定一个明确的"支持截止日"。** 验收文档里写明：免费支持期到某日为止，之后的问题走商务续签或工单。不写死这个日期，"最后一个问题"永远不会到来。

## 六、练习与自测

这套能力没法靠读书获得，但可以用自己的环境练出肌肉：

1. **完整演练一次"带事故的上线"。** 在个人服务器或虚拟机上部一个小应用（一个 FastAPI + PostgreSQL 的 demo 就够），写一份分钟级 Runbook，然后**故意制造故障**——改错一个配置、灌满磁盘、写死一个迁移——练习按 Runbook 回滚和按 SOP 处置。故意翻车三次，你就不会再怕半夜的电话。
2. **给自己的项目配齐"最小运维三件套"**：cron 备份且每月恢复演练一次、Uptime Kuma 或等价存活监控、logrotate。成本是一个下午，换来的是对"无人值守系统"的真实体感。
3. **写三份模板收进自己的模板库**：上线 Runbook、事故报告、交接清单。每个新项目直接复用并迭代，一年后这就是你区别于"会写代码的人"的资产。

自测标准——以下每条都能给出肯定答案：

- [ ] 我的每次上线有书面 Runbook，含前置条件、每步预期结果、量化回滚触发条件，且上线前演练过
- [ ] 数据管道切换前做过新旧对账，差异容忍度有业务方的书面确认
- [ ] 我经手的每次数据库破坏性变更都拆成了 expand / contract 两步
- [ ] 出事时我的第一反应是恢复而非查根因，且恢复前会先抓现场证据
- [ ] 我能拿出最近一份事故报告，包含时间线、根因和带期限的防复发动作
- [ ] 我的告警分级后，P1 告警每月少于 3 次，且每一条都真的需要立即处理
- [ ] 上一个交接的系统，客户 IT 能不联系我完成重启和备份恢复

## 小结

上线与运维的核心就一句话：**把依赖临场发挥的事，全部提前变成文件、脚本和演练过的动作**——上线靠 Runbook，切换靠对账，回滚靠演练，事故靠 SOP，移交靠清单。工程师的价值不在于出事时力挽狂澜，而在于让"出事"本身变得稀少而可控。
