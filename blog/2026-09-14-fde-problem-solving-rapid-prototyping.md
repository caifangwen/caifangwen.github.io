# FDE 快速原型与迭代：48 小时原型从做出来到用起来的完整打法

> 本文是《FDE 技能栈全景图》系列的三级专题文，深入展开「问题求解能力」支柱下的「快速原型与迭代」。父级概览见 [FDE 技能栈深入（二）：问题求解能力](./2026-09-14-fde-problem-solving.md)，系列主文见 [FDE 技能栈全景图](./2026-09-14-fde-skill-stack-pillar.md)。

## 一个典型的周二上午

客户的信息化处长把你叫过去：「上次那个库存看板，王总看了觉得不错，想再加一个维度——能不能按供应商看呆滞库存？这周集团要来检查，周五能看吗？」

现在是周二上午十点。你面对的选择是：

- A：满口答应，回工位开始改正式系统的代码，动数据模型、加接口、改前端，祈祷周五前不出岔子；
- B：说「我下午先给您出个东西看看方向对不对」，然后花三小时用真实数据做一个只验证「按供应商看呆滞库存」这一件事的粗糙原型，下午四点演示，拿到反馈后决定怎么做。

父级文章讲了 48 小时法则和原型工具箱的概览。这篇专题解决的是更细一层的问题：**时间盒之内，每一个小时怎么花；保真度选哪一级；反馈拿回来怎么分辨真假；原型验证完之后，代码和知识分别往哪去。**这些是做砸过几次原型之后才会有的颗粒度。

## 一、先想清楚：这个原型要验证什么假设

原型的唯一 KPI 是「多快拿到有效反馈」，而反馈是否有效，取决于你有没有把假设说清楚。动手之前，强迫自己写完这句话：

```
本原型验证的假设：__________
验证成功的标志：客户看到 ______ 时会 ______
验证失败的信号：客户 ______
```

拿开头的例子填一下：

```
本原型验证的假设：「按供应商维度下钻呆滞库存」能帮王总在集团检查时说清责任归属。
验证成功的标志：王总（或处长）能指着某一行说出「这个供应商要找采购部谈」。
验证失败的信号：对方纠结「呆滞的定义不对」「还缺一个维度」——说明问题定义偏了，不是图表问题。
```

注意第三条的价值：**预先定义失败信号，你才能在演示现场认账。**很多人演示时听到负面反馈会本能地解释「这个后面会做」「这只是初版」，本质是演示前没想清楚什么叫失败。听到失败信号是好事——你只花了三小时，而不是三周。

常见坑：一个原型背着三四个假设一起验证。「顺便把权限也做了」「顺便把导出也加上」。假设多了，反馈混在一起，你分不清客户不满意的是方向还是细节。一个时间盒，验证一件事。

## 二、保真度阶梯：大多数原型不需要写代码

原型的成本不是线性的，是按保真度指数上升的。选错保真度是新手最常见的浪费。我把它分成五级：

| 级别 | 形态 | 成本 | 适合验证的假设 |
|---|---|---|---|
| L1 纸面/白板 | 手绘草图 | 10 分钟 | 信息架构：「这几块内容是不是你要的」 |
| L2 静态 Mock | Figma / Excel 画的假界面 | 1-2 小时 | 样式偏好：「领导要的排版和重点标红」 |
| L3 假数据交互 | Streamlit/前端写死数据，可点击 | 半天 | 交互流程：「这个操作路径你用得顺手吗」 |
| L4 真实数据单点 | 接一张真实的表，核心逻辑可算 | 1-2 天 | 口径与价值：「算出来的数对不对、有没有用」 |
| L5 端到端薄片 | 数据管道 + 界面打通最小链路 | 3-5 天 | 可行性：「这条路技术上跑得通吗」 |

两条经验法则：

- **从你能承受的最低保真度开始。**处长要「按供应商看呆滞库存」，第一步是 L2——打开 Excel，把昨天的库存快照拉个透视表加条件格式，十分钟。如果对方看了一眼说「对，就是这个意思，但呆滞标准要按 180 天不是 90 天」，你省下了一整天。
- **升级保真度必须有触发条件**：低一级的假设已经验证通过。L2 确认了维度和口径，才值得上 L4 接真实数据算一遍。没验证就升级，等于在沙子上盖楼。

FDE 现场的高频错误是直接从 L4 起步——工程师的本能是「先连数据」。但对「样式、维度、给谁看」这类假设，L4 是杀鸡用牛刀；反过来，对「这个指标算出来跟业务认知对不对得上」这类假设，L1-L3 全是无效验证，必须上真实数据。**假设的类型决定保真度的级别**，这就是为什么第一节要求先把假设写下来。

## 三、时间盒解剖：48 小时怎么花

以一个标准的两天原型（L4 级）为例，给一个经过实战的时间分配。它反对工程师「先写 80% 代码再准备演示」的本能：

**第一天上午（3 小时）：数据与口径**

- 1 小时：拿到数据的最小可用子集（下一节展开怎么拿）；
- 1 小时：用 SQL 或 pandas 把核心口径算出来，手工抽查 3-5 行和业务对数；
- 1 小时：和懂业务的人（不一定是提出需求的人，一线最懂数据的往往是具体操作员）核对口径——「呆滞按最后出库日算还是按入库日算」这种问题，不问清楚后面全是白干。

**第一天下午（4 小时）：骨架界面**

- 用最熟的工具把界面搭出来，把上午算好的数填进去；
- 只做一条主路径：打开 → 选筛选条件 → 看到核心结果。导出、打印、权限、多 tab，全部不做；
- 下班前发一条消息：「明天上午十点给您看第一版，十分钟就够。」**先把演示的时间钉死**，这是防止时间盒无限滑动的锚。

**第二天上午（2 小时）：演示准备**

- 准备演示脚本（第五节展开）、录屏、离线副本；
- 自己按脚本完整跑一遍，掐表，超过十分钟就砍内容。

**第二天上午十点：演示，十分钟，剩下五十分钟聊反馈。**

**第二天下午：整理反馈清单发给客户确认，决定下一轮迭代还是转工程化。**

可以看到，写代码的时间只占一半不到。另外一半花在口径核对、演示准备和反馈上——而这些恰恰是「原型是否拿到有效反馈」的决定性因素。

## 四、现场约束：真实数据怎么拿到、怎么脱敏

父级文章强调过「用真实数据，哪怕是脏的」。这一节讲现场的具体操作，因为「拿不到数据」是原型阶段最真实的卡点。

**降低门槛的四个阶梯，逐级尝试：**

1. **要导出文件，不要数据库账号**。让客户 IT 从系统里导出一张 CSV/Excel，比申请数据库只读账号快得多——前者业务部门自己就能干，后者要走安全审批。
2. **要昨天的快照，不要实时接口**。原型不需要实时性，一份隔夜静态数据完全够用，省掉所有网络和权限问题。
3. **要一百行，不要一百万行**。跟客户说「先给我抽 200 行能代表各种情况的样例数据」，对方给起来心理压力小得多，你处理起来也快。
4. **实在不行，手工构造「真实结构」的数据**。找一线要一张真实的（可脱敏的）单据，照着它的字段、格式、取值习惯造 50 行假数据。这比凭空编的数据强十倍——字段命名、编码格式、脏数据的形态都是真的，演示时客户的反馈质量完全不同。

**脱敏是高压线，原型阶段尤其容易出事**——为了赶进度把含客户真实姓名的表直接投屏演示，现场翻一次车，后面所有数据权限都会收紧。最低要求：

```python
import pandas as pd
import hashlib

df = pd.read_csv("inventory_export.csv")

# 人名/公司名哈希化，保留可关联性（同一个名字哈希后仍一致）
def mask(s):
    return "S_" + hashlib.md5(str(s).encode()).hexdigest()[:6] if pd.notna(s) else s

df["supplier_name"] = df["supplier_name"].apply(mask)
df["contact_phone"] = "***"  # 电话这类字段原型里根本用不到，直接抹掉
```

原则：**原型用不到的敏感字段，读进来那一刻就删掉，不要留着「以防万一」**。不确定能不能用的数据，先不用——这是系列主文里就定下的红线。

## 五、工具深挖：三个被低估的现场利器

父级文章给了工具箱概览（Jupyter、Streamlit、Gradio、Figma），这里补三个深度用法层面的东西。

### DuckDB：原型阶段的单机数仓

客户给的是五六个 CSV/Excel/Parquet 文件，为原型搭一个数据库太重，纯 pandas 又要在内存里手工对齐 join 键。DuckDB 刚好填这个空——零安装负担（一个二进制或 `pip install duckdb`）、直接对文件写 SQL：

```sql
-- 直接 join 两个不同来源的文件，不用建库导数
SELECT s.supplier_id, s.supplier_name,
       sum(i.qty * i.unit_cost) AS idle_value
FROM read_csv_auto('inventory.csv') i
JOIN read_csv_auto('suppliers.csv') s USING (supplier_id)
WHERE datediff('day', i.last_outbound_date, DATE '2026-09-12') > 180
GROUP BY s.supplier_id, s.supplier_name
ORDER BY idle_value DESC;
```

Python 里 `duckdb.sql("SELECT ... FROM df")` 还能直接查内存里的 DataFrame。原型阶段的数据探索、口径验证、跨文件关联，一个工具全包，而且换到正式环境时这些 SQL 大部分能直接迁移。

### Streamlit 的两个工程细节

几十行出界面这件事父级讲过了。原型做多了会踩的两个坑：

- **缓存**：每次交互重跑全脚本，数据一大演示就卡。数据加载加 `@st.cache_data`：

```python
@st.cache_data(ttl=3600)
def load_data():
    return duckdb.sql(QUERY).df()

df = load_data()
```

- **版本标注**：界面上永远显示版本号和日期，比如标题栏写 `呆滞库存看板 v0.3 (09-14)`。客户内部会截图流转，没有版本号，一周后没人说得清「王总看的是哪一版」，反馈会安到错误的版本上。这是个一分钟成本、极低成本极高收益的习惯。

### Marimo / Jupyter 的选择

纯分析验证用 Jupyter 没问题。但如果原型要留给客户业务人员自己玩，Jupyter 的「cell 执行顺序污染状态」是灾难——客户从上往下乱点一气，看到的数和你说的是两回事。Marimo（反应式 notebook，改一个 cell 自动重算依赖它的所有 cell）解决了这个痛点，且能直接导出成可运行的应用。这是近两年值得换上的新工具。

## 六、演示与反馈：一场演示的工程化

演示不是展示成果，是一次设计好的反馈采集实验。

**演示脚本模板（十分钟版）：**

```
0:00-1:00  一句话定位：「这是验证 XX 假设的原型，不是成品，
           丑的地方都知道，重点看 XX。」
1:00-4:00  按真实业务场景走一遍主路径（用他们昨天的真实数据）
4:00-6:00  演示一个「啊哈时刻」：最能体现价值的一个操作
6:00-8:00  故意展示一个你不确定的设计，问：「这里我们想了两种做法……」
8:00-10:00 收尾：「接下来最需要您帮我们确认的是 XX」
```

几个关键技巧：

- **用「昨天」的真实业务场景讲**。不要说「这里是筛选功能」，要说「比如王总周五要查华东区呆滞超 180 天的库存，就是这样点两下」。客户在真实叙事里才能发现自己真正的需求。
- **预留一个「故意不确定」的口子**。人都倾向于对别人的成品客气，你主动暴露一个待定设计，等于给客户发了一张「批评许可证」，反馈质量立刻上来。
- **反馈记录当场做，按三类分**：

```
□ 方向错误（要重来的）——例：「呆滞应该按库龄不是按最后出库」
□ 迭代改进（下轮做的）——例：「金额列要加千分位」
□ 二期需求（进 backlog 的）——例：「能不能打通采购系统看订单」
```

演示后一小时内把这份分类清单发到群里请客户确认。这个动作同时完成三件事：防止记忆偏差、展示迭代速度、为「砍需求」提供依据——二期需求进公开清单，和问题定义页对齐排优先级（父级文章的 MVP 刀法，这里不再重复）。

- **分辨信号与噪音**：一个客户的「我不喜欢这个颜色」是噪音；三个客户分别说出「我看不懂这个数怎么来的」是信号——说明口径透明度是普遍问题。个体意见看内容，重复出现的意见看模式。**宁可错过一条好建议，不要被单一大嗓门（往往是职级最高的人）带偏方向。**大嗓门的意见要接，但接的方式是「您这条我们记下了，和其他几位的反馈一起看优先级」，而不是当场推翻设计。

## 七、验证通过之后：代码扔掉，知识留下

原型验证完成，最危险的念头是「在这个基础上继续开发」。父级文章把「舍不得扔原型」列为坑，这里给一个可操作的重写判断标准——满足任意两条，就该重写：

- 原型代码超过 500 行，或开始出现「不敢动的地方」；
- 需要加权限、多用户、调度、审计中的任何一项；
- 有第二个开发者要参与；
- 客户要求部署到正式环境给更多人用。

重写时，真正要从原型带走的不是代码，是**萃取出来的业务知识**。花一小时把它们写成文档，这是原型阶段最保值的产出：

```
# 呆滞库存口径说明（v1.0，与采购部张三 09-14 确认）

- 呆滞定义：库龄 > 180 天（以 last_outbound_date 为基准，
  无出库记录的按 inbound_date）
- 排除项：安全库存水位线以下的备件（spare_part_flag = 1）
- 供应商归属：以最近一次采购订单的供应商为准，
  注意历史数据有约 3% 的 supplier_id 为 -1（已注销供应商，归为"其他"）
- 金额口径：qty * 最新采购单价，不用移动平均价（财务部确认的）
```

这张纸在重写时是规格说明，在三个月后客户问「这个数怎么算的」时是免责依据，在项目交接时是核心交付物。**原型的代码会死，口径文档会活到项目结束。**

## 八、常见坑（父级之外的补充）

父级文章列了五个坑：原型当产品做、舍不得扔、假数据演示、没有 Plan B、反馈不记录。这里补充三个更隐蔽的：

- **演示对象错位**。给处长演示了三次、反馈都很好，最后王总看了一眼全盘否定——因为你一直在给「没有决策权但好约的人」演示。每个关键原型阶段，识别「谁的否定能杀死这个项目」，尽早把这个人放进演示名单，哪怕只能约到十分钟。给错的人演示一百次也是原地踏步。
- **迭代节奏断档**。第一个原型反响热烈，然后你埋头做了两周「马上就好」的第二版——客户的热情是有半衰期的，大约一周。迭代节奏宁可每次进步小，也要保持「客户每周至少看到一次新东西」的频率。信任靠复利，断档一次从头再来。
- **原型环境变成影子生产**。最尴尬的局面：原型的 Streamlit 跑在你自己的笔记本上，客户业务部门每天早上等你有空开机刷新数据——你的原型在没人正式宣布的情况下「上线」了，没有运维、没有备份、没有交接。一旦你发现客户开始**依赖**原型干活（而不只是评估它），立刻升级：要么正式立项工程化，要么明确告知风险并给出切换计划。影子生产不出事则已，出事全是你的责任。

## 九、练习方法与自测标准

**练习一：四小时限时原型（练砍的手感）**

从 Kaggle 或政府开放数据随便取一份你完全不熟的数据集，虚构一个客户角色（「某连锁餐饮的运营总监想看门店异常」），限时四小时从数据到可演示原型。强制规则：第一小时必须用来写假设和数据摸底，最后一小时必须用来准备演示脚本。做十次之后，你对「四小时能装下多少东西」会有肌肉级的判断——这就是现场估时能力的来源。

**练习二：保真度降级训练**

拿一个你做过的项目，强迫自己回答：这个项目的每一个关键假设，最低可以用哪一级保真度验证？大多数人会发现自己当时在 L4 做的事情，L2 就能验证。这个练习重塑的是「先想假设、再选保真度」的条件反射。

**练习三：三分钟电梯演示**

给不懂你项目的同事讲你的原型，三分钟，结构固定：这是什么、解决谁的什么问题、现在验证到哪一步、下一步是什么。讲不清说明你自己没想清——演示能力就是问题定义能力的外化。

**自测标准（能全部答「是」，说明这一主题过关）：**

- [ ] 我能在动手前用一句话写出原型要验证的假设，并定义成功/失败信号？
- [ ] 我能说清楚当前这个假设应该用哪一级保真度验证，为什么？
- [ ] 我的 48 小时计划里，非编码活动（口径核对、演示准备、反馈整理）占到一半？
- [ ] 我知道在客户现场拿到真实数据的最小阻力路径，并能当场完成基础脱敏？
- [ ] 我的每次演示有脚本、有录屏 Plan B、有版本号？
- [ ] 我的反馈清单按「方向错误/迭代改进/二期需求」分类，并在演示后当天发出确认？
- [ ] 我能判断原型何时该重写，并能产出一份口径文档作为重写依据？
- [ ] 我识别得出「客户开始依赖原型干活」的时刻，并知道怎么处理？

## 结语

快速原型的本质不是「做得快」，而是**用最小的代价购买「确定性」**——每一次迭代都是在问客户「是这个意思吗」，而客户看到一个能点的东西时给出的答案，比一百页需求文档都诚实。保真度控制成本，时间盒控制节奏，口径文档留住价值，剩下的全是对人的功夫。
