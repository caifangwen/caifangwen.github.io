# FDE 深挖专题：需求挖掘与问题定义——在客户说出口之前找到真问题

> 本文是《FDE 技能栈全景图》系列下「问题求解能力」支柱的三级细分专题，聚焦**需求挖掘与问题定义**。父级文章 [FDE 技能栈深入（二）：问题求解能力](./2026-09-14-fde-problem-solving.md) 已经讲了 5 Why、现场观察、问题重述和一页纸问题定义的框架，本文在此基础上再深一层：讲访谈怎么设计、数据怎么替你说真话、伪需求怎么识别、验收标准怎么锁死。

## 开篇：一个差点做砸的下午

驻场第二周，客户的信息部主任把你叫过去：「我们的设备巡检还是纸质的，你给我们做一个移动巡检 App 吧，要拍照上传、要定位、要离线可用。」需求清晰、功能明确，听起来可以直接排期了。

你多问了一句：「巡检数据现在最后流向哪里？」主任愣了一下：「流向哪？……巡检表收上来，文员录进 Excel，月底给安监科汇总。」你再问：「安监科拿汇总做什么？」「做设备健康度分析，给检修计划排优先级。」

你跟着文员坐了一个下午，发现真相：三百多台设备，每月巡检表两千多张，文员录 Excel 要四个工作日，错误率她自己都不敢算；安监科的「健康度分析」其实是拿肉眼扫一遍 Excel，把「看着不对劲」的设备标黄。而巡检工人那边，纸质表最大的痛点根本不是「要手写」，而是**很多设备的巡检项三个月前就该改了，表还是旧版**——他们勾的项目里有一半已经不存在。

最后的交付物里没有 App。第一期是：一套巡检项主数据表（解决「表是旧版」）、一个基于现有企业微信 H5 的填报页面（客户本来就有企业微信，不用装任何 App）、一条定时管道直接把数据灌进安监科的库。三周上线，文员的四个工作日变成了零。

如果那天下午你接了「移动巡检 App」就走，三个月后交付的会是一个没人愿意装的 App——巡检工人嫌手机操作比打勾慢，安监科拿到的还是月底才能看的死数据。

这个案例说明本文的核心论点：**需求挖掘的质量，在动手写第一行代码之前就已经决定了项目的生死。**父级文章给了框架，本文给你操作手册。

## 一、访谈之前：准备比提问更重要

新手 FDE 的访谈失败，80% 败在没准备。带着一张白纸去「聊聊」，得到的必然是对方的标准口径。访谈前做三件事。

### 1.1 画一张迷你干系人地图

需求来自人，人带着立场。访谈前先回答三个问题：

- 这件事**谁受益、谁受损、谁无感**？受损者不会当面反对你，但会在数据权限、配合排期上消极抵抗——他们的「需求」要格外小心地听。
- 谁是**最终用户**，谁是**付款方**，谁是**验收方**？三者经常不是同一拨人，需求冲突几乎必然出现（见第五节）。
- 每个人被什么考核？「大区总要看三个指标」的背后是「大区总周三要被点名」——考核方式决定了什么才是「够用」。

不需要很正式，笔记本上画三列名字就够了，但这张图决定你访谈的**顺序**：先聊边缘角色练手、收集背景词汇，再聊核心用户，最后聊决策层——这时候你已经能用对方的行业黑话对话，信任度完全不同。

### 1.2 准备假设清单，而不是问题清单

直接写「我要问什么」容易写成问卷调查。更好的做法是写**假设清单**：基于已有信息（客户的文档、历史报表、你查到的行业惯例），写下你对现状的猜测，访谈的目的是证伪它们。

```
假设清单示例（巡检项目）：
1. [待验证] 巡检表模板超过 6 个月没更新过
2. [待验证] 数据录入延迟 ≥ 3 个工作日
3. [待验证] 安监科的实际分析动作是"肉眼看 Excel"，
   没有成文的判定规则
4. [已证伪] 巡检工人有统一的智能终端（实际：一半人用的
   是老人机 → App 方案直接出局）
```

带着假设去访谈，你的问题会自动变得具体：「上次巡检项调整是什么时候、谁发起的、改了多久才发到工人手里？」——这种问题对方没法用套话回答。

### 1.3 准备好「道具」

空对空聊流程，客户描述的永远是「应该的流程」。带上道具能瞬间把对话拉到地面：

- 打印一张他们**现有的报表/单据**，指着上面问：「这一列的数据是从哪来的？这个数上个月为什么突然翻倍？」
- 如果你有权限，先跑几条探查 SQL 再去聊（见第四节），带着数据里的异常去问，一问一个准。

## 二、访谈之中：提问的技术

### 2.1 问题的三层结构

一次有效访谈的问题分三层，顺序不能乱：

1. **开放式开场**：「你们现在这件事是怎么做的？」——让对方把流程完整讲一遍，你只记笔记不评价。这一层收集的是对方的叙事框架。
2. **具体化追问**：对方说「然后我们汇总数据」，你问「具体怎么汇总？谁、用什么工具、花多长时间？上个月那次能给我看看吗？」——**凡是形容词（慢、麻烦、不准）都要换成名词和数字**。「很慢」翻译成「每周二下午两点开始，四个人，弄到凌晨」才有价值。
3. **假设性收口**：「如果有一种方式，周二下午五点这三个数自动出现在你邮箱里，代价是你们部门要出人每周核对一次口径——你们愿意吗？」——用假设方案测试对方痛点的真实深度。愿意付出代价的痛才是真痛。

### 2.2 三套直接可用的话术

**挖「上一次」**——人对抽象问题的回答会撒谎（不是恶意，是自我美化），对具体事件不会：

> 「不要讲一般情况。上个月，这件事最糟的一次是什么样的？从头讲。」

「上一次的故事」里藏着真实的异常处理、真实的工作量、真实的甩锅链条，这些才是你的系统要消化的东西。

**挖「 workaround 」**——用户自己发明的土办法，是需求最密集的地方：

> 「这个流程里，有没有哪一步是你们自己琢磨出来的、不在任何制度文件里的做法？」

那个助理的 VLOOKUP 映射表、那个导出系统「下午四点后必超时所以早上先导」的土经验——每个 workaround 都是一条没被满足的需求，而且是用户已经用行动投票过的需求。

**挖「不做会怎样」**——测试优先级：

> 「如果三个月后这件事还是现在这样，最难受的是谁？具体难受在哪？」

答不上来的需求，往后排。答得声情并茂的需求，就是你的切入点。

### 2.3 三种要避免的问法

- **诱导式**：「你们是不是觉得现在特别慢？」——你替对方把答案说完了，他只需要点头。改成：「现在这个过程，从启动到拿到结果，大概多久？」
- **方案式**：「你们需要一个带审批流的系统吗？」——这是推销不是挖掘。你关心的问题永远是问题本身，方案是你回家之后的事。
- ** future 式**：「未来你们想要什么功能？」——人对未来的自己的想象完全不可信。把「想要什么」换成「上周你为哪件事加了班」。

### 2.4 访谈记录的模板

别相信记忆。每次访谈后一小时内（趁着细节还在）按固定格式整理：

```
# 访谈记录：2026-09-20 / 安监科 张工 / 45min

## 关键事实（对方说的、我看到的）
- 每月 25 号收齐巡检表，文员录入需 4 个工作日
- 上月录入抽查 50 张，发现 7 处错误
- "健康度分析"无书面规则，凭张工个人经验

## 原话摘录（重要的话记原话，不要转述）
- "我眼睛扫一遍，觉得不对的标黄" ← 说明判定规则不存在

## 我的推论（与事实分开写，防止污染）
- 推论：张工即将退休，经验没有沉淀，这是隐性风险，
  但没有当面验证，下次找机会确认

## 待验证 / 下一步
- 向文员要一份上月原始表和录入后的 Excel，核对错误率
```

「事实 / 原话 / 推论」三栏分离是关键纪律——三周后你会忘记哪些是你看到的、哪些是你脑补的。

## 三、现场观察（Shadowing）进阶：带着清单去看

父级文章讲了「跟着一线坐半天」，这里给一张可直接打印的观察清单。观察时你盯着五类东西，而不是笼统地「看」：

- **系统与文件**：他打开了几个系统、几个 Excel、几张纸？每多一个数据源，你的接入成本加一分。
- **人际依赖**：哪一步需要「找人要」？微信、电话、吼一嗓子都算——凡是靠人传的环节，都是断点，也是自动化的机会点。
- **等待与空转**：他在等什么？等系统响应、等别人回复、等领导签字。等待时间就是流程的真实瓶颈，而它永远不会出现在任何流程图上。
- **手工判断**：哪一步他在「看着办」？盯着问「你凭什么判断这个对那个错」——这就是你要编码成规则的业务逻辑，也是最可能「只存在于他脑子里」的部分。
- **错误与返工**：有没有做错重来、互相核对的环节？返工率高的环节，价值密度最高。

当天回去画 as-is 流程图，标注每一步的耗时、系统、负责人、痛点，发给客户确认。这张图在需求阶段的地位，相当于架构图在开发阶段的地位。

## 四、让数据替客户说真话：数据驱动的需求挖掘

访谈和观察告诉你客户「以为」的问题，数据告诉你「实际」的问题。两者经常不一致，而不一致的地方往往就是项目的价值所在。

拿到库权限后（这是驻场第一周就该推动的事），跑这几个方向的探查：

**量与趋势**——验证「这个问题有多大」：

```sql
-- 客户说"最近投诉激增"，先验证是不是真的
SELECT date_trunc('month', create_time) AS mon,
       count(*) AS cnt
FROM complaints
GROUP BY 1
ORDER BY 1;
```

**分布与长尾**——客户描述的是「典型情况」，数据里活的才是全部情况：

```sql
-- 客户说"大部分订单当天处理完"，看看 P50/P95 怎么说
SELECT
  percentile_cont(0.5) WITHIN GROUP (ORDER BY finish_time - create_time) AS p50,
  percentile_cont(0.95) WITHIN GROUP (ORDER BY finish_time - create_time) AS p95
FROM orders
WHERE finish_time IS NOT NULL;
```

P50 是 4 小时、P95 是 9 天——中位数支持客户的说法，长尾告诉你真正痛的是那 5%，而客户描述问题时说的往往只是中间那部分。

**人工台账 vs 系统数据对撞**——最锋利的一招：

```sql
-- 业务方手工月报说上月处理 1200 单，系统里实际多少？
SELECT count(*),
       count(DISTINCT order_no)  -- 顺手查重复
FROM orders
WHERE create_time >= '2026-08-01' AND create_time < '2026-09-01';
```

系统里 1450 条、去重后 1180——三个数字对不上，每一个对不上都是一个待挖的需求或数据质量问题。注意姿势：拿着差异去问「您能帮我理解下这个差异吗」，而不是「你们的数据是错的」。前者你是来帮忙的，后者你是来找茬的。

数据探查的完整方法（空值率、编码分布、血缘摸底）在 [支柱一：核心工程能力](./2026-09-14-fde-core-engineering.md) 的数据工程篇展开，这里只强调它在需求阶段的角色：**它是你对客户叙事做事实核查的工具**。

## 五、伪需求与需求冲突：需求的「质检」环节

挖出来的需求不能照单全收，要过两道质检。

### 5.1 伪需求识别的四个信号

- **没有受害者的需求**：「这个最好也有」——问「没有这个，谁会难受」，答不上来就是伪需求。
- **领导转述的需求**：「我们领导想要一个驾驶舱」——领导本人可能只想要一个能截图汇报的数字。凡是二手需求，尽量创造机会和源头确认，哪怕只有五分钟。
- **友商驱动型需求**：「华为/阿里有这个，我们也要」——追问「有了之后你们打算用它做什么动作」，答不出具体动作的就是面子工程，做最小可汇报版本即可，别投重兵。
- **解决方案伪装型需求**：「我要 AI」——用父级文章的问题重述表翻译，翻译不动就继续挖。

### 5.2 需求冲突的处理

信息部要「数据全量采集、永久留存」，安全部门要「最小采集、到期销毁」；业务方要「下周上线」，IT 要「先过等保测评」。冲突不是异常，是常态。处理步骤：

1. **显式化**：把冲突写在纸上，标出双方各自的立场和立场背后的约束（合规压力、KPI、面子）。很多冲突一旦写清楚，双方自己就能让一步。
2. **找上位目标**：两边都不让步时，往上找一层双方都认可的目标（「不出安全事故」和「月底经营会要有数据」），围绕上位目标设计折中方案——比如「本期只接三个脱敏字段，全量接入作为二期」。
3. **升级但不站队**：涉及部门利益的你裁不了，把冲突和备选方案连同代价对比呈给双方共同的领导决策，你的角色是提供清晰选项，不是替任何一方打赢。

## 六、把定义锁死：可验收的成功标准

父级文章给了一页纸问题定义的模板，这里专门展开最容易写砸的一栏：**成功标准**。

失败的写法：「显著提升数据获取效率」——三个月后双方各说各话。合格的写法要过三重检验：

1. **有基线**：「现在文员录入耗时 4 个工作日/月」——没有基线的「提升」无法验收。基线数据来自第四节的数据探查和访谈里挖到的数字。
2. **有目标值与口径**：「上线后，三个指标在每周二 17:00 前自动刷新，与大区总助理手工核算结果逐月核对，连续两个月误差为 0」。指标、时间点、核对方式、持续周期，全部写死。
3. **有验收人**：写清楚「由安监科张工和大区总助理共同确认」。验收人必须是具体的人，不能是「业务部门」。

一个经验法则：**把成功标准想象成半年后双方关系破裂时拿去仲裁的证据**。仲裁人只看你这张纸，能不能判出谁对谁错？能，才算写到位。

## 七、常见踩坑速查

- **访谈只约会议室，不去工位**。会议室里听到的是流程的说明书，工位上看到的才是流程的尸体解剖。每场访谈尽量约在对方的工位旁边。
- **一次访谈问十个人**。群体访谈里没人说真话——说流程问题等于说在座某人的问题。深挖一律一对一，群体会议只用来确认结论。
- **把「客户确认了」当终点**。确认的是「你理解对了」，不是「这个该做」。定义完问题还要回父级文章的第三节：拆解、排期、验证数据接得进来，才叫需求阶段闭环。
- **需求阶段拖太久**。需求挖掘不是上不封顶的学术研究。一般两周内必须收敛出一页纸定义 + 一个验证性原型（见下一篇「快速原型与迭代」），挖得差不多就让原型去接棒澄清，别在访谈阶段追求完备。
- **自己补上「显然需要」的需求**。你觉得「显然需要权限管理」，客户从没提过——先问再做，「显然」是你脑补的伪需求高发区。

## 八、练习方法与自测

**三个可以立刻开始的练习：**

1. **拿内部需求练手**：从今天起，你接到的每一个需求（包括同事提的），先写一页纸问题定义再动手。内部需求试错成本低，是练翻译能力的沙盒。
2. **「上一次」复述训练**：找一个做运营或客服的朋友，请他讲工作里最烦的一件事，你只用「上一次是什么时候，从头讲」和复述确认来推进对话，练习忍住不给建议——给建议是工程师的本能，而挖掘阶段给建议就是在打断对方供词。
3. **数据核查练习**：随便找一个公开数据集或你自己系统的库，先写下三条你对数据的假设，再写 SQL 逐条证伪。练的是「先假设、后验证」的肌肉，而不是「捞到什么算什么」。

**自测清单（接到新需求后、动手前逐项过）：**

- [ ] 我访谈过至少一名真正的一线用户，而不只是管理者？
- [ ] 我至少跟着一线实际操作观察过一次，并产出了 as-is 流程图？
- [ ] 我能说出每个关键干系人「被什么考核」？
- [ ] 访谈记录里事实、原话、推论是分栏写的？
- [ ] 我至少用一条 SQL/一份原始数据核查过客户的一个说法？
- [ ] 客户的每个需求我都做过「方案→问题」的翻译？
- [ ] 我识别出并显式记录了至少一个干系人之间的冲突？
- [ ] 成功标准有基线、有目标值、有口径、有具名验收人？
- [ ] 一页纸问题定义已发出并收到书面确认？
- [ ] 「本期不做什么」写清楚了？

十条里打不满八条，回去继续挖，别动手。

## 结语

需求挖掘的全部技巧可以收敛成一句话：**对客户的方案保持怀疑，对客户的问题保持好奇，对自己的结论保持核查**——用访谈挖叙事，用观察挖真相，用数据核查两者。把问题定义对了，剩下的工程问题都是熟路；定义错了，你全栈再强也只是高速驶向错误终点。
