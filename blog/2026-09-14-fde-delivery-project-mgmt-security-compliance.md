# FDE 技能栈专题：安全与合规——驻场工程师的红线操作手册

> 系列深度专题 · 支柱五「交付与项目管理」下「安全与合规」的展开。父级文章见 [FDE 技能栈（五）：交付与项目管理](./2026-09-14-fde-delivery-project-mgmt.md)，那里讲了安全合规的原则与概貌，本文把它落到每一条可执行的操作上。

## 开篇：一个真实的现场

某能源客户现场，项目第三周。你终于拿到了生产库的只读账号，兴冲冲把两张设备表导成 CSV 拷到自己笔记本上调试清洗逻辑——里面有几万条带真实手机号的运维联系人记录。第二天客户安全部门的例行终端审计扫到了这两个文件，安全接口人直接找到项目经理：这个驻场工程师违反数据出域规定，要求立即清退，项目暂停整改。

你没有任何恶意，甚至 CSV 最终只用了一次。但在客户的安全叙事里，事实只有一条：**未授权的个人身份信息离开了受控环境，出现在了一台不受控的个人终端上**。项目停了两周，公司出面道歉、签整改承诺，你本人被换下场。

这类事故的共同点不是技术短板，而是**本能反应的缺失**：受过训练的工程师在"导出"这个动作发生的瞬间，脑子里会先弹出一个检查清单。本文的目标就是帮你把这个清单练成本能。

安全合规在父级文章里只有一节篇幅，之所以值得单独成文，是因为它有三个特殊性：一是**一票否决**——功能做得再好，一次数据事故可以清零全部信任；二是**不可逆**——延期可以追赶，泄露无法撤回；三是**追责到人**——合同上是公司责任，落到现场具体操作的人头上。

## 一、进场第一周：画出你的数据红线地图

### 1.1 为什么第一周就要做

很多 FDE 的安全问题源于一个错觉：以为安全是"上线前过评审"的事。实际上，安全约束在**数据接入的第一天**就开始生效——你能不能碰这张表、能不能导出、能存在哪，答案决定了你的架构和排期。等项目做到一半才发现某个核心数据源按分级属于"重要数据"、出域要报行业主管部门审批，排期直接崩掉。

### 1.2 怎么做：三步建立红线地图

**第一步：拿到书面的安全要求清单。** 进场第一周，主动约客户的 IT 安全接口人（如果没有专职安全部门，找信息中心负责人），索要并确认以下材料：

- 数据分级分类规定（客户内部的数据分级制度，以及本项目落在哪个行业监管框架下）
- 本项目适用的合规框架：等保级别（二级还是三级）、是否涉及个人信息（PIPL）、是否有数据出境场景（GDPR）、行业特殊规定（金融、医疗、政务各有红线）
- 数据申请、导出、传输的标准流程和审批人
- 终端管理要求：驻场电脑是否由客户提供、是否允许自带设备、装了什么终端管控软件

把这些整理成一页《项目安全要求确认单》，请对方书面回复确认。这份文件之后会在无数次"能不能这么做"的争议中保护你。

**第二步：给项目涉及的数据做分级登记。** 用一张表把每个数据源过一遍：

| 数据源 | 敏感字段 | 分级 | 能否导出 | 脱敏要求 | 审批人 |
|---|---|---|---|---|---|
| 设备台账表 | 无 | 一般数据 | 可（内网） | 不需要 | IT 张工 |
| 运维联系人表 | 手机号、姓名 | 个人信息 | 原则上不可 | 开发环境必须脱敏 | 安全部李经理 |
| 交易流水表 | 银行卡号、金额 | 敏感个人信息/重要数据 | 禁止出域 | 仅生产可用，测试用造数 | 安全部+合规部 |

**第三步：标注出"先不碰"清单。** 凡是分级不明、授权不清的表，默认放进"先不碰"清单，等书面授权下来再说。这个动作花不了你半天，但它把模糊的灰色地带变成了清晰的待办项——这正是父级文章说的"不确定能不能碰的数据，先不碰"的落地形式。

### 1.3 常见坑

- **凭感觉判断敏感度**：你觉得"车间设备数据不敏感"，客户的安全制度里它可能是"重要工业数据"。判断依据永远是客户的书面制度，不是你的常识。
- **只问业务方不问安全方**：业务负责人说"没问题你拿去用"不具备效力，数据授权必须走安全/IT 的正式流程。

## 二、数据全生命周期：每个环节的标准动作

数据在你手里会经过五个环节：**申请 → 接入 → 存储 → 使用 → 销毁**。每个环节都有标准动作，漏掉任何一个都是隐患。

### 2.1 申请：最小权限，书面留痕

- 只读账号优先，只申请需要的库和表，限定有效期（如三个月，到期续期）。
- 申请邮件里写清楚：要什么数据、用于什么目的、存在哪、谁会接触、什么时候归还/销毁。这既帮审批人做决定，也是你的免责留痕。
- 权限申请走流程期间不要闲着：让客户业务方提供一批**脱敏样本数据或导出的历史文件**先行开发（这一条在父级文章的风险管理里也强调过，它同时是进度手段和安全手段——样本文件比直连生产库好批得多）。

### 2.2 接入与存储：边界清晰，密钥入柜

- 生产数据只进受控环境（客户内网的服务器），绝不落到个人笔记本的裸盘上。如果客户提供的是加密笔记本，确认磁盘加密已开启（BitLocker / FileVault），没有就自己开。
- 数据库连接串、API Key 一律走环境变量或配置文件，且配置文件加进 `.gitignore`：

```bash
# .env 不进库，代码里只读环境变量
export DB_PASSWORD='xxx'
```

- 代码提交前过一遍密钥扫描，防止手滑把密码提交进 Git 历史。用 `gitleaks` 一行命令：

```bash
# 在仓库根目录跑，扫整个提交历史
gitleaks detect --source . -v
```

在 CI 里加一个 gitleaks 步骤，可以把这个检查自动化。**注意**：如果密码真的进了 git 历史，删掉最近一次提交不够——要改密码、用 `git filter-repo` 清历史、并通报客户安全接口人。按泄露处理，不存侥幸。

### 2.3 使用：脱敏与假数据，开发环境不见明文

这是最日常也最容易出事的环节，下一节单独展开。核心原则一句话：**生产和类生产环境之外，不出现明文敏感数据**。

### 2.4 共享与传输：只走客户认可的渠道

- 给客户发数据文件：用客户指定的内部文件平台、企业网盘或加密邮件，并保留发送记录。
- 绝不使用个人邮箱、个人网盘、个人微信/QQ 传任何含客户数据的文件——没有例外，哪怕"只是截图里有一列手机号"。截图也是数据。
- 跨网络传输（比如从内网拷到分析环境）走客户的摆渡流程，该审批审批，该登记登记。

### 2.5 销毁：离场时的收尾动作

项目结束或人员离场时，主动做三件事并留证：

1. 删除本地和测试环境的所有客户数据（含数据库 dump、CSV、日志里的数据片段）；
2. 交还所有账号权限，请客户 IT 确认账号已禁用；
3. 用邮件向客户书面确认"数据已按约定清理"，附清理清单。

这不仅是职业规范，也是对你自己的保护——离场后出了数据问题，这封邮件就是你的不在场证明。

## 三、脱敏实战：一套可直接复用的做法

### 3.1 脱敏的两个硬要求

很多文章只讲"怎么打码"，但 FDE 场景下脱敏有两个容易被忽视的硬要求：

**要求一：保持关联一致性。** 同一个手机号在客户表和订单表里必须脱敏成同一个值，否则你的测试数据 JOIN 不上，开发没法做。所以纯随机替换不行，要**确定性脱敏**：同一个输入永远映射到同一个输出。

**要求二：保持分布特征。** 数据量是百万级还是千级、空值率多少、金额的量级区间，这些特征要保留，否则性能测试和数据质量验证失去意义。

### 3.2 数据库内脱敏：视图 + 确定性映射

最简单的做法是在数据库层建脱敏视图，业务账号只能访问视图：

```sql
-- 手机号：保留前3后4，确定性（同号同结果）
CREATE VIEW v_customer_safe AS
SELECT
  customer_id,
  LEFT(phone, 3) || '****' || RIGHT(phone, 4) AS phone,
  LEFT(name, 1) || '*' AS name,           -- 姓名只留姓
  region,
  total_amount
FROM customers;

GRANT SELECT ON v_customer_safe TO biz_readonly;
REVOKE ALL ON customers FROM biz_readonly;  -- 原始表收回
```

打码（masking）保留了可读性，适合展示场景。但如果脱敏后的值还要用于 JOIN 关联，打码会丢信息，改用**带密钥的哈希令牌化**：

```sql
-- 用 HMAC 做确定性令牌化：同一手机号永远得到同一令牌，可 JOIN，不可逆推
-- PostgreSQL 需要 pgcrypto 扩展
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE VIEW v_orders_safe AS
SELECT
  order_id,
  encode(hmac(phone, '项目专用密钥-存密钥管理系统', 'sha256'), 'hex') AS phone_token,
  amount,
  created_at
FROM orders;
```

密钥放环境变量或密钥管理工具，不进 SQL 文件——上面只是示意写法，实际项目把密钥从配置里读。

### 3.3 造数：用 Faker 生成以假乱真的测试数据

对于银行卡、病历这类强敏感数据，正确姿势是**根本不进开发环境**，直接构造假数据。Python 的 `Faker` 库几行搞定，而且支持中文 locale：

```python
from faker import Faker
import csv, random

fake = Faker('zh_CN')
random.seed(42)          # 固定种子，保证可复现
Faker.seed(42)

with open('fake_customers.csv', 'w', newline='', encoding='utf-8') as f:
    w = csv.writer(f)
    w.writerow(['customer_id', 'name', 'phone', 'region', 'total_amount'])
    for i in range(1, 100001):             # 10 万行，量级贴近生产
        w.writerow([
            i,
            fake.name(),
            fake.phone_number(),
            fake.province(),
            round(random.lognormvariate(7, 1.2), 2),   # 对数正态分布模拟金额长尾
        ])
```

两个细节：一是**固定随机种子**，让假数据可复现，排查问题时"第 4213 行"才有意义；二是金额的分布刻意用了对数正态而不是均匀分布——真实交易金额是长尾的，用均匀分布的假数据测出来的报表样式和聚合性能都会失真。

### 3.4 一个隐蔽的泄露点：日志

脱敏做得再好，应用日志里 `logger.info(f"processing user {user}")` 一行就把整个对象打进去了。三条纪律：

- 日志里只打 ID 和状态，不打包含个人信息的完整对象；
- 异常堆栈注意检查——某些 ORM 的报错会把完整 SQL 和参数值带进异常信息；
- 日志文件本身按数据对待：留在受控环境，配 logrotate 定期轮转清理（同时也防磁盘撑爆，见父级文章上线与运维一节）。

### 3.5 常见坑

- **脱敏脚本只跑一次**：生产数据每次同步到测试环境都要重新脱敏，把脱敏做成管道里的固定一步，而不是一次性手工操作。
- **忘了"衍生数据"**：你基于生产数据跑出来的分析中间表、导出的 Excel 透视表，同样含敏感信息，按同一标准管理。
- **可逆脱敏当不可逆用**：简单的替换映射表如果保存不当，等于没脱敏。

## 四、审计与留痕：出事时唯一能保护你的东西

### 4.1 为什么审计日志是"保护"而不是"负担"

换个角度想：客户安全部门某天发现一批数据异常流出，第一个被怀疑的就是有数据权限的外部人员——也就是你。这时能证明清白的不是你的口头解释，而是**完整、不可篡改的访问记录**。审计日志在平安无事时是成本，在出事时是你的不在场证明系统。

### 4.2 三层留痕的最低配置

**应用层**：自建一张审计表，记录关键操作（登录、查询敏感数据、导出、修改配置）：

```sql
CREATE TABLE audit_log (
  id          BIGSERIAL PRIMARY KEY,
  actor       TEXT NOT NULL,        -- 操作人
  action      TEXT NOT NULL,        -- export / query / update ...
  object      TEXT NOT NULL,        -- 操作的表或资源
  detail      JSONB,                -- 过滤条件、行数等
  client_ip   INET,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 这张表只插不改不删，权限上收走 UPDATE/DELETE
```

**数据库层**：PostgreSQL 开启 `pgaudit`，客户等保测评经常点名要这个：

```ini
# postgresql.conf
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'ddl, write'      # 记录 DDL 和写操作；读全量太大，按需加 'read'
```

**个人操作层**：你自己驻场的关键操作——申请权限、导出数据、变更配置、清理数据——全部邮件留痕。养成习惯：凡是口头谈定的涉数据事项，挂完电话补一封确认邮件，"如理解有误请指正"。

### 4.3 日志留存时间

等保二级/三级普遍要求日志留存**不少于六个月**（这也是《网络安全法》的硬性要求）。设计存储方案时先问清客户要求的留存周期，按周期估算磁盘量，别等测评时才发现日志只能查到上个月。

## 五、依赖与镜像安全：上线前自己先扫一遍

客户安全部门在你的系统上线前通常会做漏洞扫描，扫描对象是部署包：Docker 镜像、依赖库、甚至你用的基础镜像。报告里出现高危 CVE，轻则打回整改、延误上线，重则报告抄送双方管理层——很难看。

正确姿势是在交付前自己先扫、先修。标准工具是开源的 `Trivy`：

```bash
# 扫镜像，只看高危和严重
trivy image --severity HIGH,CRITICAL myapp:1.0

# 扫代码仓库的依赖（requirements.txt / package.json / go.mod 等）
trivy fs --severity HIGH,CRITICAL .
```

离线内网怎么办：Trivy 支持离线扫描——在有网的机器下载 Trivy 二进制和漏洞库（trivy-db），拷进内网指定到本地库路径即可，官网文档有专门的 air-gapped 章节。FDE 的通行做法是：在自己的"内网交付工具箱"里常备 Trivy 二进制 + 定期更新的漏洞库。

三个低成本但高收益的习惯：

- **基础镜像用精简版**（`python:3.12-slim` 而非 `python:3.12`），攻击面小、CVE 数量通常直接降一个数量级；
- **依赖锁定版本**（requirements.txt 钉死版本号），既保证可复现，也让漏洞扫描结果可管理；
- **镜像里不带秘密**：`docker history` 能看到每一层，写在 Dockerfile 里的密码即使后面删掉也会留在历史层里。

## 六、等保与合规落地：一张影响清单

不需要背法规，但客户说"这套系统要过等保三级测评"时，你要立刻知道它对你的设计意味着什么。以等保三级为例，直接影响：

| 要求 | 对你系统的具体影响 |
|---|---|
| 身份鉴别（双因子） | 登录要 密码+短信/动态令牌 双因子，不能只有账号密码 |
| 口令策略 | 8 位以上、字母数字特殊字符混合、90 天强制更换、失败 5 次锁定 |
| 日志留存 ≥ 6 个月 | 审计日志的存储容量和归档方案按此设计 |
| 通信与存储加密 | 传输走 TLS；敏感字段存储加密；HTTPS 证书要客户内网 CA 或自建 |
| 权限三权分立 | 系统管理员、安全管理员、审计管理员角色分离——你的 RBAC 设计要预留 |
| 漏洞与补丁管理 | 建立依赖升级通道，能响应安全部门的整改通知 |

其他框架各记一句话：**PIPL** 管个人信息——最小必要、明示授权、敏感个人信息（身份证、银行卡、病历、人脸）要单独同意；**GDPR** 在外企客户或数据出境场景出现——多了删除权和出境评估；**行业合规**（金融的人行/金融监管要求、医疗的健康医疗数据安全管理办法、政务的数据不出政务网）进场第一周问安全接口人要清单即可。

项目早期必问的一句话："**这套系统要不要纳入等保测评？按几级？测评时间点是哪天？**"——答案会改变你的架构、排期甚至交付形态，问晚了的代价是返工。

## 七、与客户安全部门打交道：把守门人变成背书人

安全部门的默认姿态是"说不"，因为他们的 KPI 是不出事。硬顶没用，绕开更是死路。有效的做法是把他们拉进你的节奏里：

1. **Early review**：项目初期主动约安全接口人，带上你的数据流图（数据从哪个系统来、经过哪些组件、存在哪、谁能看），请他提意见。此时改架构的成本是一张图；上线前一周他再来拦，成本是整个项目。
2. **安全响应文档**：把他提的每条要求书面回复"如何满足、在哪个版本落实"，形成一份文档。这份文档既是交付物，也是测评时的支撑材料——你等于在帮安全接口人完成他的工作，他自然愿意帮你。
3. **拿不准先问**：临时开端口、临时导出数据这类灰色操作，问一句再做。问的动作本身就在积累信任账户，而这账户会在你某天真需要特批时兑现。

## 八、常见踩坑速查

- **生产数据留在个人笔记本**：离场清理并邮件留证，驻场电脑上的数据不属于你。
- **绕过 VPN/堡垒机图省事**：被发现一次信任清零，没有第二次。
- **个人网盘/邮箱/微信传数据**：截图也算数据，没有例外。
- **密码进 Git 历史**：按泄露处理——改密码、清历史、通报，不是删掉重提就完事。
- **只扫应用不扫镜像**：客户扫的是整个部署包，基础镜像里的 CVE 也算你的。
- **"客户没提就是没有要求"**：主动问是你的责任，"当时没说"不构成免责。
- **口头授权当授权**：涉及数据的授权必须书面，哪怕只是一封确认邮件。

---

## 九、练习与自测

**练习方法**（用个人项目就能练，不需要客户环境）：

1. 拿一个自己的小项目，走一遍全流程：写一页《安全要求确认单》模板、给数据做分级登记、用 Faker 造 10 万行假数据替换真实数据、给数据库建脱敏视图并验证 JOIN 一致性、在 CI 里加 gitleaks 和 trivy 扫描。
2. 故意制造一次"事故"演练：往仓库里提交一个假密码，然后完整走一遍处置流程（改密、清历史、写通报邮件草稿）。走一遍你就知道每个动作的真实成本。
3. 给自己系统的审计日志做一次"事后审计"：随机挑一天，能否回答"那天谁访问了什么、导出了什么"。答不出就是审计盲区。

**自测清单**：

- [ ] 说得出本项目每个数据源的敏感字段、分级、导出限制和审批人
- [ ] 手上有《安全要求确认单》和数据分级登记表两份模板，且在真实项目里用过
- [ ] 能在 30 分钟内搭出：脱敏视图（确定性、可 JOIN）+ Faker 造数脚本
- [ ] 数据库开了 pgaudit 或等价审计，应用有审计表，日志留存满足客户要求
- [ ] 交付前会用 Trivy 扫镜像和依赖，高危清零，且能在离线环境完成扫描
- [ ] 密钥全部在环境变量/密钥管理工具里，CI 里有 gitleaks 之类的密钥扫描
- [ ] 能一句话说清本项目的合规框架及它对你设计的三个具体影响
- [ ] 离场清单（数据清理、账号回收、书面确认）是肌肉记忆

## 小结

安全与合规对 FDE 来说不是一门知识，是一套本能：碰数据前先问授权、明文不出受控环境、每个操作留下痕迹、交付前自己先扫一遍。这套本能练成的标志是——你不再需要对照清单，因为每个动作发生前，检查已经在你脑子里跑完了。
