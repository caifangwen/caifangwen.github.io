# FDE 技能栈之产品思维：从交付项目到沉淀产品

> 系列子文章 · 对应 Pillar 主文章《FDE 技能栈全景图》中的「支柱四：产品思维」，展开到可执行的颗粒度。

很多工程师转 FDE 后，第一年就能熟练交付项目，但三年过去还在原地踏步——每个客户都从头发一套代码，项目结束价值就清零，汇报时只能说"我做了哪些功能"却说不出"这些值多少钱"。拉开差距的不是技术，是产品思维。

这篇文章讲清楚三件事：**怎么把现场的一次性方案抽象成可复制的产品能力、怎么用数字证明交付的价值、怎么在十个需求同时砸过来时判断做什么和不做什么**。

---

## 为什么这一支柱是 FDE 的分水岭

先把账算清楚。一个 FDE 驻场一年，人力成本按百万人民币计。如果这一年产出的是一套只能服务这一个客户的定制系统，客户一走、代码封存，公司收回的只是一个项目的合同额。但如果这一年里你还沉淀出了两个可以卖给下一个同类客户的通用模块、一份能量化续约理由的价值报告，公司收回的是这个项目合同额乘以 N 的杠杆。

这就是 Palantir 当年能从一个"驻场写代码的团队"长成产品公司的核心逻辑：**Foundry 里的每一个产品能力，最初都是某个 FDE 在某个客户现场解决的一个具体问题**。FDE 是产品公司的传感器和探针——你在现场看到的痛点、验证过的解法，是总部产品团队坐在办公室里想不出来的。

反过来说，没有产品思维的 FDE，本质上是披着工程师外衣的外包。客户要啥做啥，需求不拒绝，价值不算账，最后陷入"每个客户一套代码"的维护泥潭。所以这一支柱的三块内容——抽象、量化、取舍——是互相咬合的：**能抽象，交付才有杠杆；能量化，取舍才有依据；敢取舍，才有时间去做抽象和量化**。

## 一、从项目到产品的抽象

### 1.1 是什么

"抽象"在现场的语境里不是写个 abstract class，而是回答一个问题：**这个需求，是这一个客户的问题，还是一类客户的问题？** 如果是后者，你做的就不该是"给 A 客户定制一个功能"，而是"做一个能被 A、B、C 客户各自配置后复用的能力"。

一个真实的例子。你在制造业客户现场，客户说："我们车间设备报警太多，一天几千条，值班工人看不过来，帮我做个报警列表页面。"

- 项目思维的解法：写一个针对他们报警表结构的页面，筛选、分页、标红，两周交付，客户满意。
- 产品思维的解法：先问清楚"看不过来"的根因——80% 的报警是重复的或低优先级的。真正的问题不是"展示"，而是"报警降噪与分级"。于是你做的就不是一个页面，而是一个**可配置的报警聚合规则引擎**（同源报警合并、按严重度分级、静默时段抑制），加上一个通用展示组件。半年后你去了能源行业客户，变电站的告警泛滥是同一个问题，规则引擎换一套配置直接复用。

两种解法开发成本差 30%，但后者在第二个客户那里的边际成本接近于零。

### 1.2 怎么做：四个可落地的动作

**动作一：每次接需求时问"三个客户"问题。**

接到任何需求，强迫自己回答：

1. 这个问题换成同行业的另一个客户，会不会也有？
2. 如果答案是"有"，差异在哪里？（通常差异只在数据 schema、阈值参数、展示样式这些"配置层"，而不是核心逻辑）
3. 我能不能把核心逻辑做成通用的，把差异收敛到配置里？

如果三个问题里有肯定的答案，就在设计文档里多写一节"通用性分析"，哪怕是三行字。这个动作的成本是十分钟，收益是逼你在写代码前想清楚边界。

**动作二：把差异压进配置，而不是压进 if-else。**

现场最常见的腐化路径是：

```python
# 第一个客户
if customer == "A":
    threshold = 0.8
# 三个月后第二个客户来了
elif customer == "B":
    threshold = 0.6
    extra_field = "pressure"
```

三个月后这段代码没人敢动。正确的做法是从第一个客户起就把可变的部分抽成配置：

```yaml
# alert_rules/customer_a.yaml
aggregation:
  window: 5m
  group_by: [device_id, alarm_code]
severity:
  critical_threshold: 0.8
  fields:
    value: vibration
```

代码读配置，新客户加一份 YAML。判断标准很简单：**如果第二个客户的需求能用一份新配置满足而不用改代码，你的抽象就成功了。**

**动作三：维护一份"现场洞察"清单，定期反哺产品团队。**

FDE 是产品团队的眼睛，但眼睛看到的东西不传回去就等于瞎。做法很轻：一个共享文档或 issue 列表，每条记录包含：

```
## 现场洞察 #17
- 客户/行业：某汽车零部件厂商 / 离散制造
- 原始需求：设备报警看不过来
- 根因：低优先级报警淹没高优先级，无聚合降噪能力
- 我们的解法：规则引擎 + 分级展示（仓库链接）
- 通用性判断：同行业的设备监控场景 100% 会遇到；跨行业（能源、物业）大概率成立
- 建议：是否值得做成平台级的 Alert Intelligence 模块？
```

频率不用高，两周一条，季度和产品团队过一次。这就是 Palantir 内部 FDE 与产品团队的标准协作方式——FDE 不直接决定产品路线，但提供带证据的输入。

**动作四：守住"三次原则"再抽象。**

抽象也有成本，过早抽象是另一种灾难。经验法则：**同样的模式在三个客户（或同客户的三个场景）出现之前，不要急着平台化**。第一次，直接解决；第二次，写代码时留意通用性但不必抽象；第三次，是时候把前两次的代码重构成通用模块了。一次抽象是猜测，三次抽象才是模式。

### 1.3 常见坑

- **拿一个客户的需求去设计"通用"方案。** 你只见过一个样本，抽象出来的接口一定拟合这个样本的特殊性。等第二个客户来，接口要推翻重来。这就是为什么有"三次原则"。
- **为了通用性牺牲交付速度。** 现场的第一优先级永远是这周能跑起来的东西。正确的顺序是：先快速交付定制版拿到反馈，迭代稳定后再抽通用层。不要反过来。
- **抽象完不告诉任何人。** 你做了个好用的通用模块，埋在项目仓库深处，产品团队不知道，下一个 FDE 不知道，等于没做。抽象的最后一步是传播：写清楚 README，在内部渠道讲一次。
- **把"可配置"做成"配置地狱"。** 配置文件膨胀到 500 行、字段含义没人说得清，就是新的灾难。配置项每加一个，问一句"能不能用合理的默认值消掉它"。

## 二、价值量化

### 2.1 是什么

价值量化就是能用数字回答这个问题：**"我们驻场这一年，给客户带来了什么？"**

这不是锦上添花。续约谈判时，客户方拍板的人听到的如果是"系统运行稳定、功能持续迭代"，他无法向自己的老板证明为什么明年还要付这笔钱；但如果你说"人工对账从每周 16 人时降到 2 人时，全年节省约 730 个工时，折合人力成本约 X 万；异常发现时间从平均 3 天缩短到 4 小时，今年避免了两次批量返工"，这就是一份他自己能拿去用的续约理由。**你给他弹药，他帮你打仗。**

价值量化同时也是你自己的绩效语言，以及下一节"优先级判断"的输入——不知道一件事值多少钱，就没法判断它该不该做。

### 2.2 怎么做：四步走

**第一步：项目启动时就定基线（baseline）。**

最大的坑是项目做完了才想起来算价值，结果发现改造前的数据没人记录，"前后对比"变成"凭感觉"。所以**在动第一行代码之前**，把目标流程的现状量化下来。方法：

- 掐表：跟着一线员工完整走一遍现有流程，记录耗时。比如"导出三张表 → VLOOKUP 合并 → 人工核对 → 发邮件"，全程 90 分钟，每周 5 次。
- 查系统日志：现有流程如果是线上的，从日志里抠。工单平均处理时长、报表生成耗时、接口失败率，都有据可查。
- 问数字：错误的代价是多少？"上次数据出错导致发错货，损失多少？"——客户对损失的记忆比你想象的清晰。

把基线写进项目启动文档，哪怕粗糙。一个粗略的真实数字胜过一个精确的虚构数字。

**第二步：交付后持续测量，用同一口径。**

基线怎么量的，上线后就怎么量。如果是耗时，就再掐表；如果是系统指标，就写 SQL 定期跑。例如，管道上线后统计异常处理的平均时长：

```sql
-- 异常从产生到被处理的时长分布，按周聚合
SELECT
    date_trunc('week', created_at)          AS week,
    count(*)                                AS total_alerts,
    avg(resolved_at - created_at)           AS avg_resolution_time,
    percentile_cont(0.5) WITHIN GROUP (
        ORDER BY resolved_at - created_at
    )                                       AS median_resolution_time
FROM alerts
WHERE resolved_at IS NOT NULL
GROUP BY 1
ORDER BY 1;
```

把这类查询固化成一个每周自动更新的"价值看板"（用 Metabase、Grafana 或一张定时刷新的报表都行），让客户方干系人自己能看到数字在变好。**可 self-serve 的价值证据比你在汇报会上念 PPT 有力十倍。**

**第三步：把指标翻译成钱或时间。**

干系人看不懂"p95 延迟降低 40%"，但看得懂"每天省 3 小时"。换算公式不复杂：

```
年度节省 = 单次节省工时 × 频次 × 52周
成本口径 = 工时 × 该岗位综合人力成本（问客户 HR 或用公开薪资水平估算）
```

除了直接成本，还有三类价值别漏掉：

- **风险价值**：错误率下降避免的损失。"去年因数据错误返工 3 次，今年 0 次。"
- **速度价值**：决策周期缩短。"经营数据从 T+3 变成 T+0，早会看到的是昨天的数据。"
- **能力价值**：客户团队现在能自助做的事。"业务人员自助取数，IT 部门取数需求工单下降 60%。"

**第四步：维护一份价值登记表（Value Log）。**

一条一条记，格式随意但要持续：

| 日期 | 交付物 | 量化价值 | 证据来源 | 受益方 |
|------|--------|----------|----------|--------|
| 03-15 | 对账自动化管道 | 每周省 14 人时 | 掐表对比，财务确认 | 财务部 |
| 05-20 | 设备报警分级 | 误报处理量 -78% | 报警表 SQL 统计 | 生产部 |
| 07-08 | 经营日报看板 | 数据时效 T+3 → T+0 | 看板上线记录 | 总经办 |

这份表到续约季就是合同，到绩效季就是你的成绩单。

### 2.3 常见坑

- **夸大价值，透支信任。** 把"系统上线后销售额涨了 20%"算到自己头上——销售额涨了多少因素？客户方的业务人员一眼就能看穿。只认领你有证据链的部分，宁可少说。**价值数字的可信度比大小重要。**
- **只量化"做了的功能"，不量化"避免的工作"。** FDE 最有价值的一些工作恰恰是"劝客户不要做某个没用的系统"。这事没法写进功能列表，但可以写："评估后建议沿用现有流程，避免了一个预估 3 人月、年维护成本 X 万的冗余系统。"这也是价值。
- **测量口径偷偷变了。** 基线按"从收到数据到出报告"量，上线后按"从点按钮到页面加载"量，数字当然好看，但对不上账。口径必须一致，不一致要在报告里明说。

## 三、优先级判断

### 3.1 是什么

驻场一个月之后，你的需求来源会爆炸：拍板领导想要大屏，中层想要考核报表，一线想要少点几次鼠标，IT 部门想要你把日志接进他们的审计系统，自己公司的产品团队想让你试点新模块。十个需求同时涌来，每个提的人都觉得自己那个最急。

优先级判断就是回答三个问题：**做什么、不做什么、先做什么。** 而它的上游就是前两节——不知道价值怎么算，判断就是拍脑袋；没有产品化视角，判断就漏掉最重要的那个维度。

### 3.2 怎么做

**打分模型：价值 × 成本 × 战略意义。**

pillar 里给的三维框架，落到纸面上是一张简单的表。对每个候选需求，三项各打 1-5 分：

| 需求 | 业务价值 | 实现成本(分高=便宜) | 战略意义(可复用性) | 加权 |
|------|:---:|:---:|:---:|:---:|
| 领导要的经营大屏 | 4 | 4 | 2 | 3.4 |
| 报警聚合引擎 | 4 | 3 | 5 | 4.0 |
| 导出按钮加个 Excel 格式 | 2 | 5 | 1 | 2.6 |

- **业务价值**：直接引用上一节的方法——能省多少工时、降多少错误、影响哪个层级的干系人。注意"影响谁"是政治现实：让拍板领导每周都用到的东西，价值分天然高。
- **实现成本**：按人日粗估就够，目的是识别"一周能做完的高价值事"——这类永远排最前。
- **战略意义**：这个东西第二个客户能不能用？能做成平台能力的，优先级上浮。这就是产品思维对排期的直接介入。

模型是辅助，不是圣旨。它的真正作用是**逼你把判断显性化**：当你和 TL 或客户对优先级有分歧时，吵的是"你给成本打了 2 分我觉得是 4 分"，而不是空对空地争"我觉得这个重要"。

**砍需求的三个过滤器。**

排期之前先过滤，一半的需求活不过这三问：

1. **它在解决谁的什么问题？** 答不上来（"领导说要"不算答案，去问领导要解决什么）的，挂起。
2. **现有流程/工具真的解决不了吗？** 大量"我要个系统"的需求，用一张 Excel 模板或一条定时 SQL 就能满足。先给最轻的方案。
3. **两周后它还重要吗？** 现场很多需求是"这周领导问了一嘴"的应激产物。记下来，放进 backlog，两周后还在被提起的才排期。这一条能过滤掉惊人的比例。

**说"不"的模板。**

拒绝需求是 FDE 的家常便饭，但拒绝方式决定客户关系。差的拒绝是"做不了"或"排期满了"，好的拒绝给出替代方案和代价对比：

> "这个定制报表我们要做的话，开发加联调大概三周，而且会依赖 X 系统那个不稳定的接口，后续维护成本高。有两个替代方案：一是用现有的自助取数看板，我教小李配置，今天就能用起来，覆盖你 80% 的查询场景；二是如果确实要独立报表，我建议放到下个迭代，等 X 系统接口稳定之后，风险小很多。你倾向哪个？"

结构就是：**承认诉求合理 → 给出真实代价 → 提供替代路径 → 把选择权交回去**。客户大多数时候不是要"这个功能"，是要"问题被解决"。

### 3.3 常见坑

- **按"谁嗓门大"排期。** 领导的需求天然优先，但如果全部资源都被领导的临时想法吃掉，一线用户三个月看不到任何改善，系统落地时没人用，最后背锅的是你。要在"政治正确"和"实际价值"之间留配比，比如 60% 资源给高价值主线，40% 机动应对。
- **不敢砍，全部答应。** "好好好都做"的结果是十件事都半死不活，不如三件事彻底交付。客户对你的信任来自"你说的都兑现"，不来自"你什么都答应"。
- **优先级只定一次。** 现场的优先级每周都在变（客户组织架构调整了、政策变了、生产出事故了）。固定一个每周 30 分钟的优先级重排会议，拉客户方核心干系人一起过 backlog——让他们参与排序，他们才会认账。

## 学习路径与自测清单

### 学习路径

产品思维没法靠看书学会，但可以刻意练习：

1. **入行 0-6 个月**：先做"价值量化"这一件事。从自己手头的项目开始，写基线、跑对比 SQL、建 Value Log。这是三项里最容易独立练习的。
2. **6-18 个月**：练抽象。每接一个需求强制回答"三个客户"问题，代码评审时盯"差异是否被压进配置"。读一点经典——《Inspired》（ Marty Cagan ）讲产品价值判断，《The Pragmatic Programmer》里的正交性章节讲抽象分寸。
3. **18 个月以上**：练取舍和反哺。主动主持优先级排序会议，开始给产品团队写现场洞察，参与一次续约谈判——亲眼看价值数字是怎么变成合同的。

### 自测清单

- [ ] 我能说出当前项目三个核心交付各自的量化价值，并报出证据来源
- [ ] 项目启动文档里有基线测量，不是项目结束后补的
- [ ] 我维护着一份持续更新的 Value Log
- [ ] 最近一个需求我回答过"三个客户"问题，且设计文档里有一节通用性分析
- [ ] 我的代码里客户差异收敛在配置文件中，加新客户不用改代码
- [ ] 我两周内向产品团队反馈过至少一条现场洞察
- [ ] 我有一张显性打分的需求优先级表，且和客户方一起 review 过
- [ ] 上个月我至少拒绝或降级过一个需求，并给出了替代方案
- [ ] backlog 里挂着"观察中"的需求，两周后确认仍重要才排期
- [ ] 我说得出"我们没做什么"，和"我们做了什么"一样清楚

## 结语

技术决定 FDE 能不能把东西做出来，产品思维决定做出来的东西值不值——能不能复制、能不能算账、敢不敢取舍。这是从"驻场工程师"长成"业务伙伴"的那道坎。
